对 `HEAD` 与用户指定的固定点之间 diff 的双维度审查：

- **标准（Standards）**：代码是否符合本仓库成文的编码规范？
- **规格（Spec）**：代码是否如实实现了原始 issue / 规格的要求？

两个维度以**并行子代理**运行，避免互相污染上下文，随后由本 skill 汇总它们的发现。

issue 跟踪器应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户所说的固定点是什么就用什么（某个 commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果用户没有指定，就先询问。

一次性记下 diff 命令：`git diff <fixed-point>...HEAD`（三个点，因此比较基于 merge-base）。同时用 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

在继续之前，确认固定点能够解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的 ref 或空 diff 应当在这里就失败，而不是等到两个并行子代理内部才失败。

### 2. 确定规格来源

按以下顺序寻找原始规格：

1. commit 信息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），按照跟踪器文档中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果都没找到，询问用户规格在哪里。如果用户说没有规格，**规格（Spec）**子代理将跳过并报告"无可用规格"。

### 3. 确定标准来源

在仓库中搜索所有记录了"代码应当如何编写"的文件。当 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在时，必须将其列入清单。

无论仓库自身成文规范如何，标准（Standards）维度始终附带下文的**坏味道基线**：一组固定的 Fowler 代码坏味道（《Refactoring》第 3 章），即使仓库没有任何文档也适用。约束它的有两条规则：

- **仓库规范优先。** 成文的仓库规范永远胜出；凡是规范认可的做法，即使基线会标记它，也压制该坏味道。
- **永远是判断题。** 每个坏味道都是一条带标注的启发式提示（"可能是依恋情结"），绝非硬性违规。与本处其他标准一样，凡是工具已强制执行的内容一律跳过。

每个坏味道按*它是什么* → *如何修复*来读；对照 diff 逐一匹配：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字看不出它做什么或存什么。→ 重命名；如果起不出一个诚实的名字，说明设计本身是含混的。
- **重复代码（Duplicated Code）**：同一逻辑形状在变更中的多个 hunk 或文件里出现。→ 提取出共享的形状，让两处都调用它。
- **依恋情结（Feature Envy）**：一个方法访问别的对象的数据多于访问自己的。→ 把方法搬到它依恋的数据所在的对象上。
- **数据泥团（Data Clumps）**：同几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 把它们捆成一个类型，传递该类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串顶替一个本该拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：对同一类型的同一 `switch`/`if` 级联在变更中反复出现。→ 用多态替换，或让两处共享同一个映射表。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑变更迫使 diff 中许多文件散落各处地修改。→ 把总是一起变化的内容收拢进一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因为多个互不相关的原因而被修改。→ 拆分它，让每个模块只因一个原因而变化。
- **夸夸其谈通用性（Speculative Generality）**：为规格并不存在的需求而添加的抽象、参数或钩子。→ 删掉它；内联回去，直到真实需求出现。
- **消息链（Message Chains）**：调用方不该依赖的长串 `a.b().c().d()` 导航。→ 把这段遍历藏在首个对象的一个方法背后。
- **中间人（Middle Man）**：一个几乎只做向下转发的类或函数。→ 砍掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：一个忽略或覆盖了所继承大部分内容的子类或实现者。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

在同一条消息中、以前台方式发出两个子代理调用，并汇总它们返回的报告。

**标准（Standards）子代理的提示词**应包含：

- 完整的 diff 命令与 commit 列表。
- 第 3 步找到的标准来源文件清单，**外加第 3 步的坏味道基线全文粘贴**（子代理没有其他途径拿到它）。
- 任务简报："按文件/hunk（在相关处）报告：(a) diff 违反成文标准的每一处：引用该标准（文件 + 具体规则）；(b) 你发现的任何基线坏味道：说出其名称并引用对应 hunk。区分硬性违规与判断题：违反成文标准可以是硬性的，但基线坏味道永远是判断题，且成文的仓库规范优先于基线。凡是工具已强制执行的一律跳过。不超过 400 词。"

**规格（Spec）子代理的提示词**应包含：

- diff 命令与 commit 列表。
- 规格的路径或获取到的内容。
- 任务简报："报告：(a) 规格要求了、但缺失或只完成一部分的需求；(b) diff 中没人要求过的行为（范围蔓延）；(c) 看似已实现、但实现看起来不对的需求。每条发现都引用规格原文。不超过 400 词。"

如果规格缺失，跳过规格子代理，并在最终报告中说明这一点。

### 5. 汇总

在 `## 标准（Standards）` 与 `## 规格（Spec）` 两个标题下呈现两份报告，原样呈现或稍作清理即可。**不要**合并发现或重新排序，因为这两个维度是有意分开的（见_为什么分两个维度_）。

以一行总结收尾：每个维度的发现总数，以及_每个维度之内_最严重的问题（如有）。不要跨维度选出唯一的"最严重者"：那正是这种分离所要防止的重新排序。

## 为什么分两个维度

一个变更可能通过了其中一个维度、却通不过另一个：

- 完全遵守每一条标准、却实现错了东西的代码 → **标准通过，规格不通过。**
- 恰好做了 issue 要求的事、却破坏了项目惯例的代码 → **规格通过，标准不通过。**

分开汇报，才能防止一个维度掩盖另一个维度。
