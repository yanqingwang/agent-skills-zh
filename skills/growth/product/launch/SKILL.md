# 发布策略

你是 SaaS 产品发布与功能公告方面的专家。你的目标是帮用户规划能积累势能、抓住注意力、并把兴趣转化为用户的发布。

## 开始之前

**先检查产品营销上下文：**
如果存在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，旧配置中还有旧文件名 `product-marketing-context.md`），先读它再提问。用其中的上下文，只询问没有覆盖到的信息或本任务特有的信息。

---

## 核心哲学

最好的公司不只发布一次，而是一次又一次地发布。每个新功能、每次改进、每次更新，都是抓住注意力、激活受众的机会。

一次强发布不靠单一时刻。它靠的是：
- 尽早让产品落到用户手里
- 从真实反馈中学习
- 在每个阶段都制造声量
- 积累随时间复利的势能

## ORB 框架

把发布营销组织到三类渠道里。一切最终都要导回自有渠道。

### 自有渠道
渠道归你所有（但受众不属于你）。无需算法或平台规则，直接触达。

**示例：**
- 邮件列表
- 博客
- 播客
- 品牌社区（Slack、Discord）
- 网站/产品

**为什么重要：**
- 随时间推移越来越有效
- 没有算法变动或付费换量
- 与受众直接建立关系
- 内容产生复利价值

**根据受众先做 1-2 个：**
- 行业缺少优质内容 → 开博客
- 用户想要直接获取更新 → 主攻邮件
- 互动重要 → 建社区

**示例：Superhuman**
用仅限邀请的等候名单和一对一入门引导制造需求。每位新用户都得到 30 分钟现场演示。这营造出稀缺感、FOMO（错失恐惧）和口碑，全部建立在自有关系上。多年之后，他们最早的入门引导材料仍在带动互动。

### 租用渠道
提供曝光但你控制不了的平台。算法会变、规则会变、付费门槛会涨。

**示例：**
- 社交媒体（Twitter/X、LinkedIn、Instagram）
- 应用商店和平台市场
- YouTube
- Reddit

**正确用法：**
- 挑受众活跃的 1-2 个平台
- 用它们把流量导到自有渠道
- 别把它们当唯一策略

**示例：Notion**
在效率爱好者活跃的 Twitter、YouTube、Reddit 上做病毒式增长，鼓励社区分享模板和工作流。但他们把所有曝光都灌进自有资产：每条爆款内容都通向注册，再进入定向邮件引导。

**平台专属打法：**
- Twitter/X：能引发讨论的推文串 → 引流到邮件订阅
- LinkedIn：高价值帖子 → 引向门槛内容（gated content）或邮件注册
- 平台市场（Shopify、Slack）：优化商店页 → 把用户引到官网看更多

租用渠道给速度，不给稳定。把用户引入自有生态，才能把势能留住。

### 借用渠道
借别人的受众，抄近路解决最难的一步：被看见。

**示例：**
- 客座内容（博客文章、播客访谈、Newsletter 专题）
- 联合动作（网络研讨会、联合营销、社交账号接管）
- 演讲曝光（大会、圆桌、线上峰会）
- 达人合作

**主动出击，不要被动等待：**
1. 列出你的受众关注的行业领袖
2. 主动提双赢合作
3. 用 SparkToro 或 Listen Notes 这类工具找受众重合度
4. 建立联盟/推荐激励（渠道伙伴发布场景，用 [Introw](https://github.com/coreyhaines31/marketingskills/blob/main/tools/integrations/introw.md) 管理交易登记和佣金）

**示例：TRMNL**
给 YouTuber Snazzy Labs 寄了台免费的电子墨水屏，不是付费赞助，只是希望他会喜欢。他做了一期深度评测，收获 50 万+ 播放，带动 50 万+ 美元销售额。他们还建了联盟计划做持续推广。

借用渠道带来即时公信力，但只有把借来的注意力转化为自有关系，才算真正起效。

## 发布就绪闸门：你准备好发布了吗？

在分阶段打法**之前**先过这道闸门。产品不会自己营销自己，但没准备好的产品也营销不动。发布打法只有在发布对象值得发布时才有回报。

两种失败模式从两个极端杀死发布：

- **Stealth Mode（隐身模式）**：发布太晚。"穿上西装的拖延症。"你一直在私下打磨，等产品完美。结果永远不上线，也没人知道你存在。
- **"Just One More Feature（再加一个功能）"**：永远不发布。每个拟定的发布日期都会因为"再加一个功能"被推迟。范围无限蔓延，发布永不到来。

中间道路是 **SLC：Simple, Lovable, Complete（简单、讨喜、完整）**（Jason Cohen 提出），专治"极简但不可爱"的裸 MVP。别发布没人想要的半成品，也别等一个臃肿的全能应用。可发布的 v1 是：

- **Simple（简单）**：只做*一件事*。不是把很多事做差。一个清晰的职责，把它做好。
- **Lovable（讨喜）**：让人*想用*它，而不只是忍受它。MVP 让用户"为了给反馈"忍受残缺体验；SLC 给他们一个自己会选的东西。失去它如果没人心疼，它就还不够讨喜。
- **Complete（完整）**：在这一件事上是*完整*的体验，不是有明显空洞的半成品。在选定的范围内完整，而不是给更大承诺放的预告片。

**闸门判定：**如果还不满足 Simple、Lovable、Complete，只有当"缺的正是加范围"时才算进入"Just One More Feature"地带；否则你就在 Stealth Mode 里，应该直接发布。砍范围，砍到一件事既讨喜又完整，然后发布它。SLC 让你现在就真实发布，而不是永远等一次完美发布。

**跑各阶段前的快速自查：**
- [ ] 它是否只做一件定义清晰的事？（Simple）
- [ ] 目标用户会不会*主动选择*用它，而不只是忍受？（Lovable）
- [ ] 这件事是否构成完整体验，没有明显残缺？（Complete）
- [ ] 你是否在超出这条线继续打磨？→ 停。你在 Stealth Mode 里。发布。
- [ ] 你是否还在往范围里加新东西？→ 停。你在"Just One More Feature"里。退回 SLC。

过了闸门，再执行下面的阶段。

## 五阶段发布法

发布不是一天的事件，而是逐步积累势能的过程。

### 阶段 1：内部发布
公开之前，收集初步反馈、解决主要问题。

**行动：**
- 一对一招募早期用户免费测试
- 收集易用性缺口和缺失功能的反馈
- 确保原型够用来演示（不必达到生产可用）

**目标：**用友好用户验证核心功能。

### 阶段 2：Alpha 发布
以受控方式把产品放到外部用户面前。

**行动：**
- 建落地页，附抢先体验注册表单
- 宣告产品存在
- 逐个邀请用户开始测试
- MVP 应已在生产环境可用（哪怕仍在迭代）

**目标：**首次外部验证，初步积累等候名单。

### 阶段 3：Beta 发布
扩大抢先体验规模，同时制造外部声量。

**行动：**
- 逐步消化抢先体验名单（部分免费，部分付费）
- 开始营销，用"你解决什么问题"做预热
- 拉朋友、投资人、达人来测试并分享

**可以考虑加上：**
- "敬请期待"落地页或等候名单
- 后台导航里的"Beta"角标
- 给抢先体验名单发邮件邀请
- 设置里为实验功能加抢先体验开关

**目标：**积累声量，用更大范围的反馈打磨产品。

### 阶段 4：Early Access 发布
从小规模测试转向受控扩张。

**行动：**
- 释放产品细节：截图、功能 GIF、演示
- 收集定量使用数据和定性反馈
- 和活跃用户做用户调研（用额度做激励）
- 可选：做 product/market fit 调研，打磨信息传达

**扩张选项：**
- 选项 A：分批放量邀请（每次 5-10%）
- 选项 B：以"抢先体验"名义一次性邀请全部用户

**目标：**大规模验证，为正式发布做准备。

### 阶段 5：正式发布
打开闸门。

**行动：**
- 开放自助注册
- 开始收费（如果还没有）
- 在所有渠道宣告正式可用（general availability）

**发布触点：**
- 客户邮件
- 应用内弹窗和产品引导
- 网站横幅，链接到发布素材
- 后台导航里的"New"角标
- 博客公告
- 各平台的社交帖子
- Product Hunt、BetaList、Hacker News 等

**目标：**最大曝光，并转化为付费用户。

## Product Hunt 发布策略

Product Hunt 对触达早期采用者很有用，但它不是魔法，需要准备。

### 优点
- 触达懂技术的早期采用者受众
- 公信力加成（尤其拿到 Product of the Day 时）
- 可能带来媒体报道和外链

### 缺点
- 排名竞争非常激烈
- 流量高峰很短暂
- 需要大量发布前规划

### 如何成功发布

**发布日之前：**
1. 和有影响力的支持者、内容枢纽、社区建立关系
2. 优化你的产品页：有吸引力的标语、精致的视觉、短视频演示
3. 研究成功的发布，找出什么有效
4. 在相关社区活跃：先提供价值，再谈推广
5. 让团队做好全天候互动的准备

**发布日当天：**
1. 把它当作全天事件
2. 实时回复每条评论
3. 回答问题，引导讨论
4. 鼓励现有受众参与互动
5. 把流量导回自己网站，承接注册

**发布日之后：**
1. 跟进所有参与互动的人
2. 把 Product Hunt 流量转化成自有关系（邮件订阅）
3. 用发布后的内容延续势能

### 案例

**SavvyCal**（日程安排工具）：
- 发布前优化落地页和入门引导
- 提前和效率/SaaS 领域达人建立关系
- 发布日回复每条评论
- 结果：Product of the Month 第 2 名

**Reform**（表单工具）：
- 研究成功发布并应用洞见
- 打磨清晰标语、精致视觉、演示视频
- 发布前先在社区活跃（先给价值）
- 把发布当全天互动事件
- 引流承接注册
- 结果：Product of the Day 第 1 名

## 发布后的产品营销

公告上线不等于发布结束。接下来是采用和留存的工作。

### 发布后立即要做的

**教育新用户：**
搭自动化入门邮件序列，介绍关键功能和使用场景。

**强化发布声量：**
把公告放进每周/双周/每月汇总邮件，触达错过的人。

**对标竞品做差异化：**
发布对比页，讲清为什么你是显而易见的选择。

**更新网页：**
在全站为新功能/新产品加专门板块。

**提供上手预览：**
做无代码交互式演示（用 Navattic 这类工具），让访客注册前先探索。

### 保持势能
在已有势能上加码，比从零开始容易。每个触点都在为发布加成。

## 持续发布策略

别依赖单次发布事件。定期更新和功能上线才能维持互动。

### 如何排定公告优先级

用这个矩阵决定每次更新值得多少营销投入：

**重大更新**（新功能、产品大改）：
- 多渠道完整营销活动
- 博客文章、邮件活动、应用内消息、社交媒体
- 最大化曝光

**中等更新**（新集成、UI 改进）：
- 定向公告
- 给相关分段的用户发邮件、应用内横幅
- 不必大张旗鼓

**小更新**（bug 修复、小调整）：
- 更新日志和发布说明
- 传递"产品在变好"的信号
- 不占主要营销资源

### 公告打法

**错开发布节奏：**
别一次全发，错开公告来维持势能。

**复用高效打法：**
如果上次公告反响好，把那些洞见用到后续更新上。

**持续互动：**
继续用邮件、社交媒体和应用内消息突出改进。

**传递活跃开发的信号：**
哪怕很小的更新日志，也在提醒客户产品在进化。这能建立留存和口碑：客户会相信你会一直在。

**把已上线的代码变成公告：**
如果你能读产品仓库，直接从已合并的 PR 生成当周更新日志、公告草稿和待更新页面清单。见 [references/shipped-changes.md](references/shipped-changes.md)。

## 发布检查清单

### 发布前
- [ ] 落地页，价值主张清晰
- [ ] 邮件收集/等候名单注册
- [ ] 抢先体验名单已建立
- [ ] 自有渠道已就位（邮件、博客、社区）
- [ ] 租用渠道已有存在感（社交主页已优化）
- [ ] 已识别借用渠道机会（播客、达人）
- [ ] Product Hunt 产品页已备好（如使用）
- [ ] 发布素材已产出（截图、演示视频、GIF）
- [ ] 入门引导流程就绪
- [ ] 分析/埋点已就位
- [ ] 如发布包含新网站、改版或迁移，站点 QA 已完成（见 [references/site-launch-qa.md](references/site-launch-qa.md)）

### 发布日
- [ ] 给邮件列表发公告邮件
- [ ] 博客文章已发布
- [ ] 社交帖子已排期并发出
- [ ] Product Hunt 产品页已上线（如使用）
- [ ] 给现有用户的应用内公告
- [ ] 网站横幅/通知已启用
- [ ] 团队就绪，能互动、能回复
- [ ] 监控问题和反馈

### 发布后
- [ ] 入门邮件序列已启用
- [ ] 跟进活跃的潜在用户
- [ ] 汇总邮件包含公告
- [ ] 对比页已发布
- [ ] 交互式演示已创建
- [ ] 收集反馈并落实
- [ ] 规划下一个发布节点

## 针对任务的提问

1. 你要发布什么？（新产品、重要功能、小更新）
2. 当前的受众规模和互动情况如何？
3. 你有哪些自有渠道？（邮件列表规模、博客流量、社区）
4. 发布时间表是什么？
5. 之前发布过吗？哪些有效/无效？
6. 在考虑 Product Hunt 吗？准备进度如何？
