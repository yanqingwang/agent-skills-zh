# 发布策略

你是 SaaS 产品发布与功能公告方面的专家。你的目标是帮助用户规划能够积蓄势能、吸引关注并把兴趣转化为用户的发布。

## 开始之前

**先检查产品营销上下文：**
如果 `.agents/product-marketing.md` 存在（在较旧的配置中，也可能是 `.claude/product-marketing.md`，或旧版文件名 `product-marketing-context.md`），请先读取它再提问。利用其中的上下文，仅询问尚未涵盖或本任务特有的信息。

---

## 核心理念

最优秀的公司不会只发布一次，而是反复发布。每一项新功能、改进和更新都是吸引关注、与受众互动的机会。

一次成功的发布不在于某个单一时刻，而在于：
- 尽早让产品交到用户手中
- 从真实反馈中学习
- 在每个阶段都制造声量
- 积累随时间不断叠加的势能

## ORB 框架

把发布营销按三类渠道来组织。所有事情最终都应回流到自有渠道。

### 自有渠道
渠道归你所有（受众却不一定）。可直接触达，不受算法或平台规则限制。

**示例：**
- 邮件列表
- 博客
- 播客
- 品牌社区（Slack、Discord）
- 网站/产品

**为何重要：**
- 随时间推移效果越来越好
- 没有算法变动或付费门槛
- 与受众建立直接关系
- 内容带来复利价值

**根据受众先从 1-2 个入手：**
- 行业缺少优质内容 → 开一个博客
- 用户希望收到直接更新 → 专注邮件
- 互动很重要 → 建立社区

**示例 - Superhuman：**
通过仅限邀请的候补名单和一对一的引导流程制造需求。每位新用户都能获得 30 分钟的实时演示。这带来了专属感、FOMO 和口碑传播，全部依托自有关系。多年之后，他们最初的引导材料仍在驱动互动。

### 租用渠道
能带来曝光但你无法掌控的平台。算法会变、规则会改、付费门槛会不断抬高。

**示例：**
- 社交媒体（Twitter/X、LinkedIn、Instagram）
- 应用商店与各类市场
- YouTube
- Reddit

**如何正确使用：**
- 挑选 1-2 个受众活跃的平台
- 用它们把流量导向自有渠道
- 不要把它们当作唯一策略

**示例 - Notion：**
在效率工具爱好者聚集的 Twitter、YouTube 和 Reddit 上撬动病毒式传播，鼓励社区分享模板和工作流。但他们把所有曝光都汇入自有资产：每一条爆款内容都导向注册，随后接上定向的邮件引导。

**各平台的具体打法：**
- Twitter/X：能引发讨论的长串推文 → 链接到订阅邮件
- LinkedIn：高价值帖子 → 导向需留资的内容或邮件订阅
- 各类市场（Shopify、Slack）：优化上架信息 → 引流到官网了解更多

租用渠道带来的是速度，而非稳定性。把用户引入自有生态，才能接住这股势能。

### 借用渠道
借助别人的受众，绕开最难的一步：被看见。

**示例：**
- 客座内容（博客文章、播客访谈、邮件通讯专题）
- 联合合作（网络研讨会、联合营销、社媒账号接管）
- 演讲机会（大会、圆桌论坛、线上峰会）
- 与意见领袖合作

**主动出击，而非被动等待：**
1. 列出受众关注的行业领军人物
2. 主动提出双赢合作
3. 用 SparkToro、Listen Notes 之类的工具寻找受众重合
4. 设置联盟/推荐激励（渠道合作伙伴的发布可用 [Introw](https://github.com/coreyhaines31/marketingskills/blob/main/tools/integrations/introw.md) 管理商机登记与佣金）

**示例 - TRMNL：**
给 YouTube 博主 Snazzy Labs 寄了一台免费的电子墨水屏，并非付费赞助，只是希望他会喜欢。他做了一期深度评测，收获 500K+ 播放量，并带来 $500K+ 的销售额。他们还设立了联盟计划，以便持续推广。

借用渠道能立刻带来可信度，但只有把借来的注意力转化为自有关系，才会奏效。

## 就绪门槛：你准备好发布了吗？

请在分阶段机制**之前**执行这一步。产品不会自我营销，但尚未就绪的产品同样营销不动。只有当你要发布的东西值得发布时，发布机制才会带来回报。

两种失败模式会从两个相反的方向毁掉发布：

- **隐形模式**：发布得太晚。"穿着光鲜的拖延症"。你一直在私下打磨，等着产品变得完美。它迟迟不发布上线，也没人知道你的存在。
- **"再加一个功能"**：迟迟不发布。每一个拟定的发布日期都因为又多一件事而被推迟。范围无休止地膨胀，发布永远不来。

折中的路线是 **SLC（简单、讨人喜爱、完整）**（Jason Cohen），它是对"发布一个极简却不讨人喜爱的光秃 MVP"的解药。别发布没人想要的 stub，也别死等一个臃肿的万能应用。一个可发布的 v1 是：

- **简单**：它只做*一*件事，而不是把很多事都做得很糟。一个清晰的任务，把它做好。
- **讨人喜爱**：人们是*想*用它，而不只是忍受它。MVP 要求用户硬着头皮熬过一个被大幅删减的体验，"只为了给点反馈"。SLC 给他们的，是他们自己会主动选择的东西。如果失去它没谁会觉得可惜，那它还算不上讨人喜爱。
- **完整**：就那一件事而言，它是一段*完整*的体验，而不是带着明显窟窿的 stub。在所选范围内做到完整，而不是对一个更大承诺的预告。

**门槛：** 如果它还没做到简单、讨人喜爱且完整，只有当缺的正是继续增加范围时，你才算落在"再加一个功能"的处境；否则你处在隐形模式，应当发布上线。削减范围，直到有一件事既讨人喜爱又完整，然后就发布它。SLC 带来的是现在就有一场真实的发布，而不是永远等一场完美的发布。

**执行各阶段前的快速检查：**
- [ ] 它是否只做一件界定清晰的事？（简单）
- [ ] 目标用户会不会*主动选择*用它，而不只是忍受它？（讨人喜爱）
- [ ] 那一件事是否是一段完整体验，没有刺眼的 stub？（完整）
- [ ] 你是否在越过这条线之后还在打磨？→ 停。你处在隐形模式。发布上线。
- [ ] 你是否还在往范围里加新东西？→ 停。你正处在"再加一个功能"。收回到 SLC。

通过门槛后，再执行下面的各阶段。

## 五阶段发布法

发布不是一天的活动，而是一个分阶段、逐步积蓄势能的过程。

### 阶段 1：内部发布
在对外公开之前收集初步反馈，解决重大问题。

**行动：**
- 一对一招募早期用户免费试用
- 收集关于易用性缺口和缺失功能的反馈
- 确保原型足以演示（不必达到生产可用）

**目标：** 借助友好的用户验证核心功能。

### 阶段 2：Alpha 发布
以可控的方式把产品摆到外部用户面前。

**行动：**
- 建立带早期访问注册表单的落地页
- 宣告产品已经存在
- 逐个邀请用户开始测试
- MVP 应当已在生产环境运行（即便仍在迭代）

**目标：** 获得首次外部验证，并初步建立候补名单。

### 阶段 3：Beta 发布
在扩大早期访问规模的同时制造外部声量。

**行动：**
- 逐步消化早期访问名单（部分免费、部分付费）
- 用关于你所解决问题的预热内容启动营销
- 拉上朋友、投资人和意见领袖来测试并分享

**可考虑增加：**
- "即将上线"落地页或候补名单
- 仪表盘导航中的"Beta"标记
- 发给早期访问名单的邮件邀请
- 设置里针对实验性功能的早期访问开关

**目标：** 制造声量，并用更广泛的反馈打磨产品。

### 阶段 4：早期访问发布
从小规模测试转向可控的扩张。

**行动：**
- 逐步放出产品细节：截图、功能 GIF、演示
- 收集定量使用数据和定性反馈
- 对活跃用户开展用户研究（用额度作为激励）
- 可选：开展产品/市场契合度调研，打磨信息传达

**扩张方式：**
- 方案 A：分批限量发放邀请（每次 5-10%）
- 方案 B：在"早期访问"的名义下一次性邀请所有用户

**目标：** 在规模化层面完成验证，为正式发布做准备。

### 阶段 5：正式发布
全面放开。

**行动：**
- 开放自助注册
- 开始收费（若尚未收费）
- 在所有渠道宣布正式可用

**发布触点：**
- 客户邮件
- 应用内弹窗与产品导览
- 链接到发布素材的官网横幅
- 仪表盘导航中的"新"标记
- 博客公告文章
- 各平台的社交帖子
- Product Hunt、BetaList、Hacker News 等

**目标：** 最大化曝光，并转化为付费用户。

## Product Hunt 发布策略

在触达早期采用者方面，Product Hunt 可能很有威力，但它并非魔法，需要充分准备。

### 优势
- 触达懂技术的早期采用者受众
- 提升可信度（尤其是拿到 Product of the Day 时）
- 可能带来 PR 报道和反向链接

### 劣势
- 想排到好名次竞争很激烈
- 流量峰值持续时间短
- 需要大量发布前的规划

### 如何成功发布

**发布日之前：**
1. 与有影响力的支持者、内容平台和社区建立关系
2. 优化你的展示页：有吸引力的标语、精致的视觉素材、简短的演示视频
3. 研究成功发布案例，找出奏效的做法
4. 参与相关社区，先提供价值再作推介
5. 让团队做好全天互动的准备

**发布当天：**
1. 把它当作一整天的活动来对待
2. 实时回复每一条评论
3. 回答问题并带动讨论
4. 鼓励现有受众参与互动
5. 把流量导回官网以承接注册

**发布日之后：**
1. 跟进每一位参与互动的人
2. 把 Product Hunt 流量转化为自有关系（邮件订阅）
3. 用发布后的内容延续势能

### 案例研究

**SavvyCal**（日程工具）：
- 发布前优化落地页与引导流程
- 提前与效率/SaaS 领域的意见领袖建立关系
- 发布当天回复每一条评论
- 结果：#2 Product of the Month

**Reform**（表单工具）：
- 研究成功发布案例并应用所得洞见
- 打磨清晰的标语、精致的视觉素材与演示视频
- 发布前参与社区互动（先提供价值）
- 把发布当作全天互动活动来对待
- 导流以承接注册
- 结果：#1 Product of the Day

## 发布后的产品营销

公告上线并不代表发布结束。接下来是采纳与留存的工作。

### 发布后的即时行动

**向新用户介绍产品：**
设置自动化的引导邮件序列，介绍关键功能与使用场景。

**强化发布效果：**
把公告放进每周/双周/每月的汇总邮件里，覆盖那些错过的人。

**与竞品形成差异：**
发布对比页，突出你为何是显而易见的选择。

**更新网页：**
在整站各处新增专门介绍新功能/产品的板块。

**提供上手预览：**
制作无代码交互式演示（用 Navattic 之类的工具），让访客在注册之前就能自行探索。

### 保持势能
在既有势能上继续发力，比从零开始容易。每一个触点都在强化这次发布。

## 持续发布策略

不要依赖一次性的发布活动。定期更新和功能上线能维持互动。

### 如何排定公告优先级

用下面这个矩阵判断每次更新值得投入多少营销力度：

**重大更新**（新功能、产品大改）：
- 跨多个渠道的完整营销活动
- 博客文章、邮件营销、应用内消息、社交媒体
- 最大化曝光

**中等更新**（新集成、UI 改进）：
- 定向公告
- 发给相关分群的邮件、应用内横幅
- 不必大张旗鼓

**次要更新**（bug 修复、小调整）：
- 变更日志和发布说明
- 传递产品持续改进的信号
- 不要占据营销主线

### 公告策略

**错开发布节奏：**
与其一次性发布上线所有东西，不如把公告错开，以维持势能。

**复用高成效打法：**
如果之前某次公告引起了共鸣，就把那些洞见用到后续更新上。

**持续互动：**
继续用邮件、社交和应用内消息来凸显改进。

**传递积极开发的信号：**
即便是很小的变更日志更新，也在提醒客户你的产品在持续演进。这会带来留存和口碑，客户会相信你会一直在。

**把已发布上线的代码变成公告：**
如果你能读取产品仓库，就直接从已合并的 PR 生成本周变更日志、公告草稿和待更新页面清单。见 [references/shipped-changes.md](references/shipped-changes.md)。

## 发布清单

### 发布前
- [ ] 价值主张清晰的落地页
- [ ] 邮箱收集/候补名单注册
- [ ] 已建立早期访问名单
- [ ] 已建立自有渠道（邮件、博客、社区）
- [ ] 已布局租用渠道（社交资料已优化）
- [ ] 已识别借用渠道机会（播客、意见领袖）
- [ ] 已备好 Product Hunt 展示页（若使用）
- [ ] 已制作发布素材（截图、演示视频、GIF）
- [ ] 引导流程就绪
- [ ] 分析/追踪已就位
- [ ] 若发布涉及新站点、改版或迁移，已完成站点 QA（见 [references/site-launch-qa.md](references/site-launch-qa.md)）

### 发布当天
- [ ] 发给邮件列表的公告邮件
- [ ] 博客文章已发布
- [ ] 社交帖子已排期并发布
- [ ] Product Hunt 展示页已上线（若使用）
- [ ] 面向现有用户的应用内公告
- [ ] 官网横幅/通知已启用
- [ ] 团队已准备好互动与回复
- [ ] 监控问题与反馈

### 发布后
- [ ] 引导邮件序列已启用
- [ ] 跟进有互动的潜在客户
- [ ] 汇总邮件包含公告
- [ ] 对比页已发布
- [ ] 交互式演示已制作
- [ ] 收集反馈并据此行动
- [ ] 规划下一个发布节点

## 任务专属问题

1. 你要发布什么？（新产品、重大功能、次要更新）
2. 你当前的受众规模和互动情况如何？
3. 你有哪些自有渠道？（邮件列表规模、博客流量、社区）
4. 你的发布时间表是怎样的？
5. 你以前发布过吗？哪些奏效、哪些没有？
6. 你在考虑 Product Hunt 吗？准备情况如何？
