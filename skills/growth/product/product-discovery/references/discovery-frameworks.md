# 发现框架

## 机会解决方案树（OST）

目的：持续把产品成果（outcome）与经过验证的机会、经过测试的方案连接起来。

核心结构：
- 成果（指标）
- 机会节点（需求/痛点）
- 方案构想
- 实验

OST 实践要点：
- 让树保持“活”的状态；每次访谈或测试后更新。
- 机会证据与方案提案分开存放。
- 避免只留单枝、强行导向单一方案的树。

## 待完成任务（Jobs-to-be-Done，JTBD）

用 JTBD 理解用户想取得的进展。

JTBD 模板：
"When [situation], I want to [motivation], so I can [expected outcome]."

JTBD 访谈关注点：
- 触发时刻
- 现有替代品与变通办法
- 购买/采用的顾虑
- 期望的进展与成功标准

## Kano 模型

按对满意度的影响给功能分类：
- Must-be（必备型）：预期中的基线功能
- Performance（期望型）：越多越好
- Delighters（魅力型）：意料之外的价值倍增器
- Indifferent（无差异型）：影响很小
- Reverse（反向型）：可能降低部分用户的满意度

问题验证之后给方案概念排优先级时，用 Kano。

## 设计冲刺（Design Sprint）方法论

典型阶段：
1. 理解
2. 草绘
3. 决策
4. 原型
5. 测试

在发现中的用法：
- 把学习周期压缩进一周。
- 最适合高模糊度、需要跨职能对齐的机会。

## 假设优先级矩阵

把假设映射到两条轴上：
- 判错的代价（低 -> 高）
- 确定性（低 -> 高）

优先级顺序：
1. 高风险、低确定性（先测）
2. 高风险、高确定性（快速验证）
3. 低风险、低确定性（延后）
4. 低风险、高确定性（记录在案）

## 发现证据规则

- 重大决策不能只靠单一来源。
- 定性与定量信号做三角验证。
- 执行测试前预先定好判定标准。
- 归档证据时附上日期、细分人群和方法。
