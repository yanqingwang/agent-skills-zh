# 系统化调试

## 概述

**核心原则：** 在尝试修复之前，永远先找到根因。修表面症状就是失败。

**违反这个流程的字面，就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

没有完成阶段 1，你就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况更要用它：**
- 时间紧迫（紧急情况会诱使人瞎猜）
- "就一个快速修复"看起来很明显时
- 你已经试过多个修复时
- 上一个修复没起作用时
- 你没有完全理解这个问题时

**以下情况也不要跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你在赶时间（赶时间只会保证返工）
- 经理要求现在就修好（系统化比乱试一通更快）

## 四个阶段

你必须完成每个阶段才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们经常直接包含解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查最近的改动**
   - 什么改动可能导致这个问题？
   - git diff、最近的 commit
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，先加入诊断性埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深埋在调用栈中时：**

   完整的回溯追踪技术见本目录下的 `root-cause-tracing.md`。

   **简版：**
   - 坏值是从哪里产生的？
   - 是谁带着坏值调用了这里？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**修复之前先找到模式：**

1. **寻找可用的参照示例**
   - 在同一个代码库中找到类似的可工作代码
   - 与坏掉的东西相似的东西里，什么能正常工作？

2. **对照参考实现**
   - 如果是在实现某个模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 在套用之前完全理解这个模式

3. **识别差异**
   - 能工作的和坏掉的之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖**
   - 它需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **形成单一假设**
   - 清楚地陈述："我认为 X 是根因，因为 Y"
   - 把它写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 做尽可能小的改动来验证假设
   - 每次只改一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 起作用了？是 → 阶段 4
   - 没起作用？形成新假设
   - 不要在其上叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 阶段 4：实现

**修根因，而不是修症状：**

1. **创建失败的测试用例**
   - 尽可能简单的复现
   - 有条件就写自动化测试
   - 没有测试框架就写一次性测试脚本
   - 修复之前必须先有它
   - 使用 `superpowers:test-driven-development` 这个 Skill 来编写规范的失败测试

2. **实现单一修复**
   - 针对已识别的根因
   - 每次只改一处
   - 不做"顺手"的改进
   - 不打包夹带重构

3. **验证修复**
   - 现在测试通过了吗？
   - 没有破坏其他测试吗？
   - 问题真的解决了吗？
   - 在宣称成功之前，使用 `superpowers:verification-before-completion` 这个 Skill

4. **如果修复不起作用**
   - 停下
   - 数一数：你已经试过几个修复了？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3：停下，质疑架构（见下面第 5 步）**
   - 没有架构讨论，不要尝试第 4 次修复

5. **如果 3 次以上修复都失败了：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同位置暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复都在别处制造新症状

   **停下，质疑根本：**
   - 这个模式从根本上站得住脚吗？
   - 我们是不是"纯粹因为惯性才坚持用它"？
   - 我们该重构架构，还是继续修症状？

   **在尝试更多修复之前，先和你的人类伙伴讨论**

   这不是一个失败的假设——这是一个错误的架构。

## 红色信号——停下，回到流程

如果你发现自己正在想：
- "先快速修一下，以后再调查"
- "就试着改一下 X，看看行不行"
- "多改几处，然后跑测试"
- "跳过测试吧，我手动验证"
- "大概是 X 的问题，我把它修了"
- "我没完全搞懂，但这样也许行"
- "模式说的是 X，但我换个方式改"
- "主要问题有这几个：[未经调查就直接列出修复方案]"
- 还没追踪数据流就提出解决方案
- **"再试一次修复"（已经试过 2 次以上时）**
- **每次修复都在不同位置暴露出新问题**

**以上任何一条都意味着：停下。回到阶段 1。**

**如果 3 次以上修复都失败了：** 质疑架构（见阶段 4.5）

## 你的人类伙伴在提醒你方法错了的信号

**留意这些纠偏话语：**
- "那件事没有发生吗？" - 你在没验证的情况下做了假设
- "它能让我们看到……吗？" - 你本应该先添加证据收集手段
- "别瞎猜了" - 你在不理解的情况下提出修复
- "深入想透这个问题" - 质疑根本，而不只是症状
- "我们卡住了？"（带挫败感） - 你的方法行不通

**看到这些时：** 停下。回到阶段 1。

## 常见的自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单的问题也有根因。对简单的 bug 来说，流程很快就走完。 |
| "紧急情况，没时间走流程" | 系统化调试比"猜一下试一下"的乱撞更快。 |
| "先试这个，然后再调查" | 第一个修复会定下整个模式。从一开始就做对。 |
| "我先确认修复有效，之后再写测试" | 没有测试的修复站不住。先写测试来证明它。 |
| "一次修多个省时间" | 没法隔离出哪个起了作用。还会引入新 bug。 |
| "参考实现太长，我按自己的理解改" | 一知半解必然出 bug。完整地读完它。 |
| "我看出问题了，让我修一下" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2 次以上失败之后） | 3 次以上失败 = 架构问题。质疑模式，别再修了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、检查改动、收集证据 | 理解是什么（WHAT）和为什么（WHY） |
| **2. 模式** | 寻找可用的参照示例、对比 | 识别差异 |
| **3. 假设** | 形成假设、最小化验证 | 假设得到确认或产生新假设 |
| **4. 实现** | 创建测试、修复、验证 | bug 已解决，测试通过 |

## 当流程得出"没有根因"时

如果系统化调查表明问题确实是环境性的、依赖时序的或外部因素导致的：

1. 你已经完成了整个流程
2. 把你调查过的内容记录下来
3. 实现恰当的处理（重试、超时、错误提示）
4. 添加监控/日志，供将来进一步调查

**但是：** 95% 的"没有根因"案例其实是调查不彻底。

## 辅助技术

以下技术是系统化调试的组成部分，位于本目录中：

- **`root-cause-tracing.md`** - 沿调用栈向回追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** - 找到根因之后，在多个层级添加校验
- **`condition-based-waiting.md`** - 用条件轮询替换随意的超时等待
