# 并行调试（Parallel Debugging）

一个用于调试复杂问题的框架，基于竞争性假设分析（ACH）方法，并结合并行 Agent 调查。

## 何时使用本 Skill

- bug 存在多个看似合理的根因
- 初步调试尝试未能定位问题
- 问题跨越多个模块或组件
- 需要有证据支撑的系统性根因分析
- 希望在调试中避免确认偏误

## 假设生成框架

围绕 6 类失败模式生成假设：

### 1. 逻辑错误（Logic Error）

- 条件逻辑不正确（运算符错误、遗漏分支）
- 循环或数组访问中的差一错误（off-by-one）
- 缺少边界情况处理
- 算法实现不正确

### 2. 数据问题（Data Issue）

- 无效或意外的输入数据
- 类型不匹配或类型转换错误
- 期望为值的地方出现 null/undefined/None
- 编码或序列化问题
- 数据截断或溢出

### 3. 状态问题（State Problem）

- 并发操作之间的竞态条件
- 过期缓存返回陈旧数据
- 初始化或默认值不正确
- 共享状态被意外修改
- 状态机转换错误

### 4. 集成失败（Integration Failure）

- API 契约违规（请求/响应不匹配）
- 组件之间的版本不兼容
- 不同环境之间的配置不一致
- 环境变量缺失或错误
- 网络超时或连接失败

### 5. 资源问题（Resource Issue）

- 内存泄漏导致性能逐渐劣化
- 连接池耗尽
- 文件描述符或句柄泄漏
- 磁盘空间或配额超限
- 低效处理导致的 CPU 饱和

### 6. 环境（Environment）

- 运行时依赖缺失
- 库或框架版本错误
- 平台特定的行为差异
- 权限或访问控制问题
- 时区或区域设置相关的行为

## 证据收集标准

### 何为有效证据

| 证据类型     | 强度 | 示例                                                            |
| ------------ | ---- | --------------------------------------------------------------- |
| **直接证据** | 强   | `file.ts:42` 处的代码显示 `if (x > 0)` 应为 `if (x >= 0)`       |
| **相关性**   | 中   | commit `abc123` 之后错误率上升                                  |
| **传闻性**   | 弱   | "在我机器上是好的"                                              |
| **缺失性**   | 不定 | 代码路径中未找到 null 检查                                      |

### 引用格式

引用证据时必须附带 file:line（文件:行号）引用：

```
**Evidence**: The validation function at `src/validators/user.ts:87`
does not check for empty strings, only null/undefined. This allows
empty email addresses to pass validation.
```

### 置信度等级

| 等级             | 判定标准                                          |
| ---------------- | --------------------------------------------------- |
| **高（>80%）**   | 多条直接证据、因果链清晰、无相悖证据                |
| **中（50-80%）** | 部分直接证据、因果链合理、存在少量模糊之处          |
| **低（<50%）**   | 以相关性证据为主、因果链不完整、存在部分相悖证据    |

## 结果仲裁协议

待所有调查者汇报完毕后：

### 步骤 1：结果分类

- **已确认**：高置信度、证据有力、因果链清晰
- **可能成立**：中置信度、有一定证据、因果链合理
- **已证伪**：证据与假设相悖
- **无法定论**：证据不足以确认或证伪

### 步骤 2：比较已确认的假设

如果多个假设同时被确认，按以下维度排序：

1. 置信度等级
2. 支持证据的数量
3. 因果链的强度
4. 是否缺少相悖证据

### 步骤 3：确定根因

- 如果某一假设明显占优：宣布其为根因
- 如果多个假设可能性相当：可能是复合问题（多个原因共同作用）
- 如果没有任何假设被确认：基于已收集的证据生成新假设

### 步骤 4：验证修复

在宣布 bug 已修复之前：

- [ ] 修复确实针对已识别的根因
- [ ] 修复未引入新问题
- [ ] 原始复现场例不再失败
- [ ] 相关边界情况已被覆盖
- [ ] 已添加或更新相关测试
