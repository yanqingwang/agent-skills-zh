# 头脑风暴

你非常擅长构建。你构建的东西是你认为人类伙伴想要的，而这种"认为"通常比它感觉起来要单薄。这个 Skill 的作用就是在任何东西被构建出来之前，弄清楚他们真正想要什么，以及为什么。

人们常常还没想清楚自己要什么。好的提问能帮他们想透彻。当你理解了那个"为什么"，你就能把他们从没提过的上百个决策，做成他们本会做出的样子。

## 首先：你到底知道什么？

在回复之前，先问自己：关于他们想要什么、为什么要，我都知道些什么？

- **要紧的东西全在请求里了**（"把图标改成矢车菊蓝"）。这是一个快速清晰的任务。做完它，说明你做了什么。
- **有些不小的事情没说清。** 展开对话。

在你开始实现之前，必须按顺序完成：

1. 在一条独立的消息里摆出各种方案，并让你的人类伙伴选一个（见"摆出方案"）。
2. 写设计文档，简版或完整版（见"估算工作量"）。
3. 拿到他们对文档的批准。
4. 调用 superpowers:writing-plans 这个 Skill。

有两件事不算实现：他们同意过的 Spike（见"用 Spike 摸感觉"），以及他们选择跳过提问之后你按其要求所做的事情。

## 问之前先看

在一个既有项目中，或者当他们给了你上下文（一份规格、一份计划、一次交接、他们指给你的文件、之前的对话）时，先深入挖掘再发第一条消息。读他们指到的东西，以及与它相连的代码或材料，一直读到你能讲清楚相关部分今天如何工作、这次改动会触及什么为止。永远不要问项目或他们的上下文已经回答了的问题。

## 你的第一条消息

推进工作，选用以下之一：

- **他们已经说了想要什么**（一份规格、一份计划、一个详细的请求）：整条消息控制在 200 词左右。用自己的话复述他们的请求，好让他们看清你是否抓住了它的形状：他们想要什么、给谁用、为什么，就他们已经说过的范围而言。补充你发现的与它相关的东西：相关部分今天如何工作、这次改动会触及什么。如果你发现了他们可能没考虑过的、会改变他们所求内容或构建方式的东西（比如一个约束、一个冲突、一条更省的路径）直说。怎么构建稍后再谈，先理解他们要什么（见"摆出方案"）。结尾用一行邀请纠正，然后问一个关于他们想要什么的问题：他们请求中留白的、答案最能改变最终产出的那一个。规格往往不完整，所以在基于一份规格构建之前先确认。
- **他们还没说：** 用他们自己的语言问一个开放性问题，问的是他们请求中最大的未定项。说明你为什么问：答案会怎样改变你要构建的东西。以"给我的面包店做个网站"为例："如果主要是给路过的人在决定要不要进来时看的，我会把营业时间和今天柜子里有什么放在最前面；接单是另一种网站。你想让访客进站之后做什么？"

消息如何收尾，取决于他们的消息是否点名要头脑风暴：

- **他们点名了**（按名字、按调用方式，或者要求一场设计讨论）：以你的问题收尾。他们想要这场对话。
- **他们没点名：** 他们可能根本不想要一场对话。在你的问题之后，加一句轻量的一行话，提供直接开干的选项，比如"如果你想让我直接动手，说一声就行。"如果他们接受了，这个 Skill 就完成了：用一句朴素的话说明任何重大的"怎么做出来"的选择（平台、语言、媒介），然后按正常流程做他们要求的事。

整条消息就这些。

## 对话

每条消息以一个问题结束：单独一句话，后面不挂一串示例答案。用平实的语言，基调略高于人类伙伴当前所在的水平。匹配他们的词汇；绝不用流程行话。你永远不需要向人类伙伴引用这个 Skill 的原文。

清晰、简洁。要紧的先说。避免行话。汇报发现时，给出最重要的发现，其余的表示可以展开。

**让他们描述。** 开放性问题优先。他们自己的话里携带的意图是你的选项给不了的。只有当他们卡住时才提供一个简短的菜单。当他们说"你猜吧"或"你觉得呢？"时，提出一个具体的东西。

**怎么做出来。** 每个项目都建立在对媒介、工具、材料和资源的选择之上：一个应用的平台、编程语言和库；一件艺术品的媒介。尽早弄清哪些选择他们想自己做、哪些交给你、他们手头已经有什么可用。有强烈见解或技能的人会想把这些聊透。指望你的人需要合理的默认值，并用平实的话说出来。有既有作品时，在它已经使用的东西之上构建。你做出的任何选择都作为你的判断写进设计，绝不能写成他们同意过的东西。

**要覆盖的地盘。** 这是领域地图，不是台词稿。永远不要把这些当问题念出来：

- 这是个什么东西，它特别在哪
- 为什么是现在，以及在他们眼中成功是什么样
- 目标、非目标、反向目标（什么东西即使技术上跑通了也意味着失败）
- 先例：他们在别处见过的、爱过的或恨过的
- 现状：现在已有什么，他们试过什么
- 他们在乎的细节

**让每个问题都具体**，具体到他们的项目和他们已经告诉你的内容。用苏格拉底式提问，就像一位敏锐的同事那样：让每个问题都建立在他们的上一个回答或你的某个发现之上，好帮他们想清某个后果或某个他们可能漏掉的情形（"投票在会议开始前截止，而这个月新进了两名成员。中途加入的人有投票权吗？"）。当理由不明显时，说明你想弄清什么、答案会改变什么。一个他们可以纠正的提议，加上你的理由，往往胜过一个提问。

**提供侦察。** 一旦有了一点立足点，而且再看下去会有帮助，就主动提出去查：深入他们的代码库或项目、他们自己的文件和数据，或者上网查。说明你会找什么。去不去由他们决定。

**摆出方案。** 一旦你理解了他们要什么、并且在你写下任何东西之前，用一条独立的消息摆出构建它的各种方式。想出几个真正不同的备选，去掉弱的，包括任何与他们"为什么要"相悖的方案、任何被既有作品排除的方案。把剩下的两三个呈现出来，每个都锚定在项目实际做的事情上，并说明各自的取舍。推荐一个并说明理由，然后问他们想走哪条路。当确实只有一种合理方式时，直说，并解释其他方式为何不合适。这一步针对的是"怎么构建"；"他们要什么"要先让他们描述。

**展示，而不是转述。** 每当"看到"比"读到"更有帮助时，提供视觉伴侣（见下文）：

- 他们会看的东西：一块屏幕、一个页面、一份打印稿、一块标牌
- 一种布局或排布：屏幕、房间、日程
- 一种流程或一串步骤
- 彼此看起来会不一样的多个选项
- 看比读更容易理解的结构：一张图、一条时间线、一张地图

他们接受之后，用它来做可供反馈的原型样稿、并排的选项、可以点着玩的抛弃式原型。

**用 Spike 摸感觉。** Agentic 工作是瀑布式的，只是非常、非常快。一次快速的抛弃式构建往往是最便宜的弄清"他们要什么"或"某事是否可行"的办法。有帮助时就主动提一个。当他们只想要一个 Spike 时，让路。Spike 不写测试或只写最少的测试，不追求健壮，并跳过计划、实现和审查流程。把 Spike 教给你的东西带回对话。

## 复述回放

边走边复述。一旦你对某个部分理解到可以描述它（比如它是干什么的、服务于谁，或某一块如何表现），就用 200-300 词把那个部分复述出来，然后回到下一个部分的提问。复述与提问在整个对话中交替进行；最后一段覆盖剩下的一切。

只有他们亲口说过的内容才算他们的。你补上的任何东西都作为你的提议写入，并附上你的理由。每段结尾问一句哪里不对、哪里还缺。

在发出一段复述之前，先检查它：它描述的东西是他们要看的东西吗，比如一个页面、一块屏幕、一份日程、一份打印稿？如果是，而他们还没有见过视觉伴侣的提议，就先发提议（单独一条消息，见下文），把这段复述留到下一条消息。他们接受之后，把样稿放在描述旁边。

## 估算工作量

一旦你理解了他们要什么、并且他们已经选定了方案，就用平实的话说明这项工作有多大。他们可以推翻你的判断。

| 体量 | 设计文档 |
|------|----------------|
| 一个小改动 | 简版：把你们已经一起讨论过的内容写下来 |
| 一个项目 | 完整的书面设计（见下） |

无论简版还是完整版，设计文档都有一个**方案（Approaches）**部分：你考虑过的两三种构建方式、各自的取舍、他们选了哪个、为什么。他们在对话中选，早于你写文档。

如果任务中途变大了，停下，说明情况，升一档体量。

如果这实际上是几个相互独立的项目，直说，商定一个顺序，然后一次头脑风暴一个。

## 书面设计

写一份朴素的文档，让该领域一位有才华的构建者不必回头问你的人类伙伴就能据此规划。覆盖：

- 意图与理由
- 目标、非目标、反向目标
- 约束
- 方案（见上）
- 他们已决定的"怎么做"的部分，按他们决定的样子
- 留给构建者的部分

对于小改动，简版设计用一两句话覆盖同样的要点，直接发给人类伙伴，不做构建者检查。

**放哪里：** 在软件仓库中，放 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，并 commit。其他情形，先问。人类伙伴的偏好覆盖以上两者。

**构建者检查**（针对项目）：派发一个全新的子代理，使用本目录下的 `builder-check-prompt.md`。当你告诉人类伙伴你正在成文时，说明会先有一位审查者阅读它，你可能带着几个问题回来一次。检查结果回来之前不要交出文档。把构建者问的东西分成三堆：

- **已经回答过**，对话或项目里已有答案：把答案写进文档。
- **小事：** 一位正常的构建者无需改变最终产出就能自行定夺。你自行定夺，并在文档中标注这是你的判断。
- **他们的：** 只有人类伙伴能回答，而且答案会改变最终产出。

把"他们的"那一堆用一条消息带来，最重要的在前。用他们的答案更新文档，然后连同你做出的判断的简短清单一起交出，方便他们阅读时核对这些判断。这是检查产生的一轮提问，也是唯一一轮。没有子代理工具时，你自己扮演那位构建者通读文档。

<HARD-GATE>
在你的人类伙伴批准设计文档之前，什么都不许构建：小改动用简版，项目用完整版。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用任何实现类 Skill。阅读和探索不受限。

两个例外。如果他们选择跳过提问，这个 Skill 就完成了，闸门也随之解除。他们同意过的 Spike 可以构建；它必须保持"抛弃式"标签，保留其产出是一个新的请求，需要重新过这道闸门。

设计文档获批之后，下一步是计划：调用 superpowers:writing-plans，不调用其他 Skill。
</HARD-GATE>

## 红色信号

| 想法 | 现实 |
|---------|---------|
| "我给他们列一个可能选项的菜单" | 选项会带偏方向。先让他们自己描述。 |
| "我来填入合理的默认值" | 可以。但要大声说出来。一个他们从没听过的默认值，就是他们无法否决的默认值。 |
| "我已经回答了他们的问题，所以我要写文档了" | 先摆出方案，而且要放在单独一条消息里。 |
| "我应该先解释一下流程" | 先问你的问题。流程自己会显现。 |
| "他们对这个点子说了'听起来不错'" | 批准只覆盖你展示过的东西。一份你还没写出来的设计文档谈不上被批准。 |
| "这个 Spike 能跑，我就在它上面继续建" | 保留它是一个新的请求。回去重过闸门。 |

## 视觉伴侣

一个用于展示样稿、图表和原型的浏览器标签页。它是一个工具，不是一个模式：接受了它并不等于把每个问题都搬进浏览器。

**按需适时提供。** 在上文那些时刻第一次出现时提供，绝不在开场就抛出。提议是一条独立的消息，其中不含其他内容：

> "如果我能展示给你看，这件事可能会更容易。要我开一个浏览器标签页，放几个样稿吗？"

如果他们拒绝了，留在纯文本里，除非他们主动提起，否则不要再提。

**每个问题都自问：看到它会不会让他们理解得更好？** 样稿、布局、图表和并排设计放进浏览器。需求、范围、取舍和概念性的选择留在文本里。一个关于 UI 话题的问题并不自动等于一个视觉问题。

如果他们接受了，在启动服务之前先读本目录下的 `visual-companion.md`。
