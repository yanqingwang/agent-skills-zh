# 推荐系统流水线架构师

一个用于构建可组合的推荐、排序与信息流流水线的规格与脚手架 Skill。它固化了由 xAI 开源的 [For You algorithm](https://github.com/xai-org/x-algorithm)（Apache 2.0）推广开来的六阶段模式，并将其应用于任何"为 (user, context) 挑选 top K"的问题。

## 概述

生产环境中的大多数"推荐系统"并非什么高深的 ML，而是*流水线*：从一个或多个来源拉取候选，用元数据加以丰富，剔除不合格的，给其余的打分，排序并挑出 top K，然后触发异步的副作用。这个模式是通用的。评分函数和条目会变，流水线的形状不变。

本 Skill 是对该模式的独立重新实现（MIT），没有从原始项目复制任何代码。

## 何时使用本 Skill

- 构建任何返回"针对 user/context 的 top K 条目"的系统
- 设计或重构个性化信息流（内容、搜索结果、通知）
- 把 LLM/ML 评分器包进规范的流水线配套环节（来源、数据补充、过滤器、副作用）
- 加入带可调权重的多动作预测（而非单一的相关性分数）
- 构建 RAG 检索重排器（低成本检索 → 高成本重排）
- 设计任务优先级排序器或告警分诊系统

## 六阶段框架

| # | 阶段 | 职责 | 可并行？ |
|---|---|---|---|
| 1 | **Source** | 从一个或多个来源拉取候选 | 是，多个来源并行运行 |
| 2 | **Hydrator** | 用过滤与评分所需的元数据丰富候选 | 是，多个独立的 Hydrator 并行运行 |
| 3 | **Filter** | 剔除不合格的候选（被屏蔽、已过期、重复、不合资格） | 顺序执行，每个过滤器看到的条目更少 |
| 4 | **Scorer** | 为每个存活的候选赋予一个或多个分数 | 顺序执行，后面的评分器能看到前面的分数 |
| 5 | **Selector** | 按最终分数排序，返回 top K | 单次操作 |
| 6 | **SideEffect** | 缓存、记录日志、发出事件、更新 served-history | 异步，绝不能阻塞响应 |

### 为什么是这个顺序

- 来源先于数据补充：先弄清有哪些候选，再付出成本去丰富它们
- 数据补充先于过滤：许多过滤器需要来源未提供的元数据
- 过滤先于评分：评分是成本最高的阶段，先剔除不合格的
- 评分器链（而非单一评分器）：真实系统会组合 ML 评分 + 多样性重排 + 业务规则
- Selector 放在评分之后：保持评分的确定性与可缓存性
- SideEffect 放在最后且异步：副作用绝不能阻塞用户响应

## 被调用时的工作流程

带用户走完八个步骤：

1. **明确用例**（一轮，仅在缺失时问三个问题）：被排序的条目、输入上下文、language/runtime
2. **确定候选来源**（通常是关注网络内 + 关注网络外，但单一来源同样有效）
3. **列出所需的数据补充**：对每个过滤器和评分器，它需要哪些来源未提供的数据？
4. **列出过滤器**：成本低的前于成本高的，通用的前于用户相关的（重复、本人、时长、屏蔽/静音、已服务过、资格）
5. **设计评分器链**：主 ML/启发式 → 组合器（带权重的多动作） → 多样性 → 业务规则
6. **Selector**：按最终分数降序排序，取 top K（或分层混合）
7. **SideEffects**：缓存已服务的 ID、发出曝光事件、更新计数器、记录分析日志；全部采用 fire-and-forget
8. 在用户的技术栈中**生成脚手架**

## 需要显式呈现的关键权衡

绝不要在这些点上默默采用默认值，它们其实是披着技术外衣的产品决策。

### 1. 单一分数 vs 多动作预测

- **单一分数：** 训练一个模型来预测相关性。要改变行为 → 重新训练。
- **多动作：** 为许多动作预测 `P(action)`（`P(read)`、`P(like)`、`P(share)`、`P(skip)`、`P(report)`），在服务时用权重组合。要改变行为 → 改权重，无需重新训练。

X For You algorithm 采用同时带正、负权重的多动作方式。当用户预期需要频繁调优时，推荐多动作。

### 2. 候选隔离 vs 联合评分

- **隔离式：** 每个候选独立打分，确定性、可缓存。
- **联合式：** 打分时候选之间互相关注（例如对整个 batch 跑 transformer）。表达力更强，但跨 batch 不确定。

默认采用隔离式。只有在有明确理由时才用联合式（例如显式的 batch 级多样性）。

### 3. 在线 vs 离线批量

- **请求时（在线）：** 流水线在每个请求上运行。延迟预算：100–300ms。
- **预计算（离线批量）：** 流水线周期性运行，结果被缓存。延迟更低，新鲜度更低。
- **混合式：** 候选检索离线，排序在线。

## 硬性规则

1. **不要编造基准数字。** "这个有多快？" → "取决于负载，自己跑一遍。"
2. **署名规范。** 将该模式署名为 "popularized by xAI's open-sourced For You algorithm" / `github.com/xai-org/x-algorithm`（Apache 2.0）。
3. **不使用商标。** 不要把用户的产物命名为 "X-like"，也不要使用 "For You" 品牌字样。使用中性名称："candidate pipeline"、"feed pipeline"、"ranking pipeline"。
4. **显式呈现权衡。** 多动作 vs 单一、隔离 vs 联合、在线 vs 离线，绝不默默采用默认值。
5. **生成的脚手架必须能运行。** 不许拿伪代码冒充代码。
6. **过滤器顺序很关键。** 成本低的前于成本高的，通用的前于用户相关的。
7. **副作用绝不阻塞。** 用 fire-and-forget 模式包装（goroutines / promises without await / asyncio tasks）。

## 反模式

- ❌ 先评分后过滤（把算力浪费在终将被丢弃的候选上）
- ❌ 同步副作用（缓存写入 / 曝光事件发送阻塞响应）
- ❌ 当产品需要多目标调优时却只用单一"相关性"分数
- ❌ 默认采用联合评分（不确定、不可缓存、无法与重排组合）
- ❌ 拿"仅作示意"的伪代码充数，脚手架必须真的能运行

## 常见用例

### 内容信息流（Strapi v5 插件，TypeScript）

用户的 CMS 里有 50k 篇文章，想要一个个性化的"for you"信息流。走完 8 个步骤 → 生成一个带多动作评分、作者多样性、标准过滤器和异步副作用通道的 Strapi 插件脚手架。

### RAG 检索重排器（Python async）

用户的 RAG 从向量数据库返回 top-50 个 chunk，希望用成本更高的评分器重排并返回 top-5。单一来源流水线，配一条评分器链（低成本检索 + 高成本重排）。

### 任务优先级排序器（FastAPI 服务）

用户有一队列传入的任务建议，希望结合其过往模式，按"该用户接下来该做什么"来排序。条目反过来了（是任务而非内容），但同一套形状依然适用。

### 通知分诊（离线批量作业）

用户想要一份每日摘要，从最近 24h 的队列里挑出 top 10。离线批量流水线。Source = 队列，filters = age/dedup/eligibility，scorer = urgency × user-affinity，selector = top 10，side effect = 发送邮件（仍为异步）。
