# 工作流：发布上线一项变更

一项变更只有当以下条件全部满足才算**完成**，并且报告中要逐条体现：

1. **截图**：真实渲染出的游戏的截图，开始状态、关键时刻与最终结果。它们要在报告中内联展示。
2. **专属的更新日志版本**，其图片放在游戏内更新日志页面上。
3. **已验证**：
   - 你自己的测试；
   - 你合并进来的那些 commit 的测试；
   - 资源检查；
   - 在已推送的 commit 上运行的完整测试套件。
4. **已提交**：一个内聚的 commit，只暂存你自己的文件。
5. **已推送**到 `main`，以 fast-forward 方式，并在 GitHub 上确认。
6. **已上线**：那份 `main` 的构建已发布，并在真实域名上确认可用。
7. **已测量**：commit 的尺寸、推送的尺寸、任何上传与发布的尺寸，全部实测，绝不估算。

对项目自己的仓库和线上站点，推送与发布是长期授权。所以在这些操作之前不要询问，**除非**下方某个防护栏要求停下。开工前先读项目的 `AGENTS.md`，以及本 Skill 的 `references/<project>.md`（如果存在）。项目规则经常变化，凡与本 Skill 不一致之处，以项目规则为准。

## 防护栏：停下并询问用户

- **任何超过 50 MB 的上传。** 这涵盖 git push、Netlify deploy、媒体发布，以及发送给任何外部服务的文件。
  - 先测量（用 `upload-size.sh`，或 `push-main.sh` 打印出的 pack 大小），询问时说明尺寸。
  - 按整个操作计算，绝不为了低于阈值而拆分。
  - 一次完整的 Supabase 媒体发布（约 861 MiB）始终需要询问。
- **强制推送（force-push）**、改写远端历史、更改仓库可见性，或推送到另一个仓库。
- **新的站点或项目**，或更改站点的访问方式、域名或 DNS，除非任务正是这件事且用户明确要求。
- **当权限检查拦截了**某次 deploy、rollback 或上传时：停下。不要换一种方式或通过另一个线程重试。把确切的点击路径或命令告诉用户。
- **你的发布之后线上故障：** 在报告里第一时间说明，附上实测证据和回滚的点击路径。不要把它埋没。

## 防护栏：绝不

- 绝不发布任何非干净的、已推送的 `origin/main`。不接受未合并的分支、未提交的文件。
- 绝不把大体积媒体回退部署到 Netlify；媒体放在 Supabase Storage。
- 绝不发布到项目已弃用的主机，即使旧脚本仍指向它。
- 绝不运行宽范围图片优化器（`pnpm images:optimize`，或 `optimize-images.py --apply`）。它会改写其他会话的待处理图片。请使用 `runtime-assets.py --only '<your glob>'`，然后 `--verify`。
- 绝不暂存凭证、`.env*`、`node_modules`、缓存或构建产物，在共享 checkout 中绝不使用 `git add -A`。
- 在远端或域名上确认之前，绝不把本地 commit 称为"已推送"，也绝不把 deploy 称为"已上线"。
- 绝不杀掉不是你自己启动的进程。先检查它的工作目录：`lsof -a -p <pid> -d cwd`。

## 步骤

### 0. 开始之前
- 运行 `git fetch`，然后 `git log origin/main --oneline -30`，搜索你的领域。查看同级的 worktree（`git -C <wt> diff --stat`），看是否有人正在做同样的修改。
- 在你自己的 worktree 中、基于 `origin/main` 拉出的分支上工作。其他会话会实时编辑共享 checkout。

### 1. 截图
- 使用项目的 review fixtures（`?review=<name>`），以 1600×900 截取真实游戏。截取开始、关键时刻与最终结果。
- 如果项目指定了截屏工具，就用它。否则通过 CDP 无头截屏（见 `workflow-progress-screenshots` Skill），并说明你用的是哪种。
- 每张图片使用前都要亲自看过。出现无关的 toast、过期的数字或错误的场景，就意味着重新截取。
- 诚实地为它们加标签：无头浏览器截屏，且手机尺寸的视口不等于真机测试。
- 把截屏脚本放在 worktree 中被 gitignore 的 `qa/captures/` 里；会话暂存区会在重启时被清空。

### 2. 更新日志版本
- 严格遵循项目的更新日志规则：格式、版本命名，以及图片如何添加。
- 为玩家而写：他们现在能看到或能做什么，不出现文件名或哈希。
- 对测试、工具、文档或规则的变更不获得版本号。
- 如果另一个会话占用了你的版本号，合并时重新编排你的编号，并保留它们的条目。

### 3. 验证
- 随做随跑你的变更触及的测试套件。
- 合并 `main` 之后，还要运行合入 commit 触及的每一个测试文件：`git diff --name-only <old-base> <new-base> -- tests`。
- 如果随变更发布了图片，运行图片校验。
- 在繁忙的机器上，完整测试套件要 10–40 分钟。用 `run_in_background` 运行并读取日志。看起来像超时的失败，先单独重跑一次再判定为真实失败。
- 诚实报告哪些运行是完整套件、哪些是针对性运行，附通过与失败的计数。

### 4. 提交
- 开始之前 `git diff --cached` 必须为空。
- 只暂存**显式路径**。
- 对已暂存的变更运行 `commit-size.sh`；其数字要写进报告。
- 每个内聚变更一个 commit。仍在迭代时，修订（amend）单个进行中的 commit，而不是堆积多个小 commit。
- 按仓库的风格撰写提交信息，以系统给出的署名行结尾。

### 5. 合并并推送
1. `git fetch`，然后 `git rebase origin/main`（在共享分支上则用 merge）。
2. 解决冲突时保留所有人的工作。对于生成的 JSON（图片审计、manifest），采用上游的文件，重新加入你自己的记录，并用项目的工具重算总数。
3. 对每个 `src` 和 `tests` 文件运行 `node --check`。然后运行你的测试加上合入 commit 的测试。
4. `push-main.sh`：
   - 它拒绝任何不是 fast-forward 的推送；
   - 它测量 pack 大小，超过 50 MB 就停止；
   - 它以 `--progress` 推送并打印 git 的 "Writing objects" 行（即发送的字节数）；
   - 它确认 `origin/main` 等于 HEAD。

   如果 `main` 移动了，回到步骤 1。
5. 在已推送的 commit 上运行完整测试套件，如果失败就向前修复。

### 6. 发布上线
- 在 HEAD 恰好是 `origin/main` 且被跟踪文件干净的 checkout 中构建。
- 如果构建改变了某个被跟踪的文件，先提交并推送那个文件，然后重新构建。
- 测量将要上传的内容（`upload-size.sh dist`，加上任何媒体发布）。超过 50 MB 就停下询问。
- **先部署到 draft 或 preview URL。** 运行 `verify-live.sh <draft-url>`：检查页面、它的脚本与美术资源，以及 gate 路由。只有通过后才晋升到生产环境。这个步骤的存在是因为曾有一次生产部署在缺少 edge function 的情况下就发了出去：站点能返回页面但每张图片都 404，没人玩得了。
- 晋升之后，在真实域名上运行 `verify-live.sh`。记录 deploy ID、发布时间、线上游戏版本，以及发送的字节数。
- 如果另一个会话在你之后发布了，只要它发布的也是 `main`，就没有问题。

## 报告

简短，按此顺序：

1. commit 哈希，已推送并确认。commit 尺寸：文件数、总大小、最大的文件。推送尺寸：发送的字节数。
2. 线上：URL、deploy ID、时间、线上版本，以及 `verify-live.sh` 的结果。上传尺寸：发送的字节数、构建站点的大小，以及任何媒体发布。如果你没有发布，说明原因（例如"暂缓：包含超过 50 MB 的媒体发布；询问中"）。
3. 变更内容，以玩家视角描述，加上更新日志版本号和标题。
4. 测试：哪些运行是完整套件、哪些是针对性运行，附通过与失败的计数。
5. 截图附说明文字，标注为无头浏览器截屏。
6. 任何延后或偏离的事项，以及原因。
