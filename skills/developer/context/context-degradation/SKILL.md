# 上下文退化模式

在上下文失效级联扩大之前诊断并修复它。上下文退化不是非黑即白的——它是一个连续谱，通过五种独特且可预测的模式显现：迷失在中部（lost-in-middle）、上下文污染（poisoning）、上下文分心（distraction）、上下文混淆（confusion）与上下文冲突（clash）。每种模式都有特定的检测信号与缓解策略。请把退化当作一个具有可度量阈值的工程问题，而不是不可预测的失效方式。

## 何时启用

在以下情况启用本 Skill：

- 长对话中 Agent 性能意外退化
- 调试 Agent 产生错误或无关输出的案例
- 设计必须可靠处理大上下文的系统
- 为生产系统评估上下文工程选型
- 调查 Agent 输出中的"迷失在中部"现象
- 分析 Agent 行为中的上下文相关失效

以下属于其他 Skill 负责的相邻工作，不要启用本 Skill：

- 在没有实际失效的情况下解释上下文基础机制：`context-fundamentals`。
- 在失效模式已明确之后应用 token 效率战术：`context-optimization`。
- 设计压缩整理（compaction）或交接摘要策略：`context-compression`。
- 将大输出、日志或草稿状态持久化到提示词之外：`filesystem-context`。

## 核心概念

围绕注意力的 U 形曲线组织上下文放置：开头和结尾位置获得可靠的注意力，而在长上下文实验中，中部位置的记忆准确率显著下降（claim-context-degradation-lost-middle-ruler）。这不是模型 bug，而是注意力机制的必然后果——第一个 token（通常是 BOS）充当"注意力吸收点"（attention sink），消耗了不成比例的注意力预算，随着上下文增长，中部 token 得到的注意力不足。

把上下文污染当作熔断器（circuit breaker）问题来对待。一旦幻觉、工具错误或错误的检索事实进入上下文，它就会通过反复的自我指涉不断放大。一个被污染的目标段落会让每个下游决策都在强化错误假设。检测需要追踪论断的出处（provenance）；恢复则要求回退到污染点之前，或仅用已验证内容重启上下文。

在加载上下文之前激进过滤——哪怕一篇无关文档都会可度量地降低相关任务上的表现。模型无法"跳过"无关上下文；它必须关注提供的所有内容，从而在相关与无关内容之间产生注意力竞争。把可能需要但当前不相关的信息放到工具调用背后，而不是预先加载。

隔离任务上下文以防止混淆。当上下文包含多种任务类型或在多个目标之间切换时，模型会把错误任务的约束带进来、调用适合另一上下文的工具，或混合多个来源的要求。用独立的 context window 做显式任务分割可以消除交叉污染。

通过优先级规则而非累积来化解上下文冲突。当上下文中出现多个各自正确但相互矛盾的来源（版本冲突、视角冲突、多源检索）时，模型无法判断哪个适用。显式标注矛盾、建立来源优先级，并在过时版本进入上下文之前将其过滤。

## 详细主题

### 迷失在中部（Lost-in-Middle）：检测与放置策略

把关键信息放在上下文的开头和结尾，绝不放在中部。U 形注意力曲线意味着中部位置的信息记忆准确率下降 10-40%。对超过 4K token 的上下文，这一效应会变得显著。

使用能把关键发现呈现在注意力优势位置的摘要结构。添加显式的章节标题与结构标记——它们充当注意力锚点，帮助模型在长上下文中导航。当文档必须全文纳入时，在其前面加上要点摘要，并在末尾附上关键结论。

监测迷失在中部的症状：正确信息存在于上下文中但模型忽略它、回答与提供的数据相矛盾，或模型"遗忘"了长提示词中较早给出的指令。

### 上下文污染：预防与恢复

在所有外部输入进入上下文之前进行校验。工具输出、检索到的文档和模型生成的摘要是三个主要污染向量。每一个都会引入未经证实的论断，而后续推理会将其当作事实。

通过这些信号检测污染：此前成功任务上的输出质量退化、工具错配（错误的工具或参数），以及经显式纠正仍持续存在的幻觉。当这些信号聚集出现时，应怀疑污染而非模型能力问题。

恢复方式是移除被污染的内容，而不是在其上叠加纠正。回退到污染点之前、仅保留已验证信息重启干净的上下文，或显式标记被污染的段落并要求从头重新评估。在被污染的上下文上层层叠加纠正很少奏效——原始错误仍保有注意力权重。

### 上下文分心：精选优于累积

精选进入上下文的内容，而不是指望模型自行忽略无关内容。研究表明，哪怕仅一篇干扰文档也会触发可度量的性能退化——该效应呈阶跃函数而非线性曲线。多个干扰物会让问题叠加复合。

在加载检索到的文档之前施加相关性过滤。使用命名空间（namespacing）与结构化组织使章节边界清晰。优先基于工具调用的访问而非预加载：把参考资料存放在检索工具背后，只有与当前推理步骤直接相关时才进入上下文。

### 上下文混淆：任务隔离

把不同任务分割到独立的 context window 中。上下文混淆不同于分心——它关注的是模型把错误上下文的约束应用于当前任务，而不只是注意力稀释。迹象包括：回答回应了查询的错误侧面、调用了适合其他任务的工具、输出混合了多个来源的要求。

在任务上下文之间实现清晰的转换。使用按任务隔离目标、约束与工具定义的状态管理。当单次会话内不可避免地要切换任务时，使用显式的"上下文重置"标记，指示哪些约束适用于当前片段。

### 上下文冲突：冲突解决协议

在冲突出现之前建立来源优先级规则。上下文冲突不同于污染——多条信息各自正确但相互矛盾（版本冲突、视角差异、多源检索得到分歧的事实）。

实现版本过滤，在过时信息进入上下文之前将其排除。当矛盾不可避免时，用结构化的冲突标注显式标记：说明什么与什么冲突、每个论断来自哪个来源、哪个来源优先。没有显式的优先级规则，模型对矛盾的消解是不可预测的。

### 实证基准与阈值

将这些基准用作设计约束——而非普适真理。RULER 式证据表明，宣称的长上下文支持并不保证在该长度上令人满意的任务表现（claim-context-degradation-lost-middle-ruler）。接近满分的大海捞针（needle-in-haystack）测试得分无法预测真实世界的长上下文表现。

**模型特定的退化阈值**

退化起点因模型家族与任务类型而显著不同。一般而言，对复杂检索任务，退化大约从宣称 context window 的 60-70% 开始（RULER 基准发现，宣称支持 32K+ 上下文的模型中只有 50% 能在该长度上保持令人满意的表现）。关键模式：

- **具备扩展思考（extended thinking）的模型**通过逐步验证减少幻觉，但延迟与 token 成本更高
- **面向 Agent/编码优化的模型**对工具输出密集的上下文往往有更好的注意力管理
- **拥有超大 context window（1M+）的模型**能处理更多原始上下文，但仍遵循 U 形退化曲线：更大的窗口不是消除问题，而是推迟问题

务必用你自己的具体工作负载来实测退化阈值，而不是依赖公开基准。模型特定阈值会随每次模型更新而过时（见常见陷阱 2）。

### 反直觉发现

设计上下文策略时请考虑这些有研究依据的意外：

**打乱的上下文可以胜过连贯的上下文。** 研究发现，对某些检索任务，不连贯（打乱顺序）的大海捞针堆（haystack）可以胜过逻辑有序的版本（claim-context-degradation-distractor-shuffled）。连贯的上下文可能制造干扰检索的错误关联；不连贯的上下文反而可能迫使精确匹配。不要假设组织得更好的上下文总是带来更好的结果——两种排布都要测试。

**单个干扰物就有超大影响。** 与在第一个之后追加更多干扰物相比，一篇无关文档带来的性能损失不成比例地大。把干扰物防治当作二元问题：要么保持上下文干净，要么接受显著退化。

**needle 与问题相似度低会加速退化。** 需要在不相似内容之间做推断的任务，随上下文长度增加的退化速度快于表面相似度高的任务。设计检索时让查询与被检索内容之间的语义重叠最大化。

### 何时更大的上下文反而有害

不要假设更大的 context window 能提升性能。性能在某个模型特定阈值之前保持稳定，随后快速退化：这条曲线是带悬崖的非线性曲线，不是缓坡。对许多模型而言，即使窗口支持大得多的尺寸，有意义的退化也从 8K-16K token 就开始。

把成本纳入考量：处理 400K token 上下文的时间与算力成本呈指数级高于 200K，而非线性高出。对许多应用而言，这使大上下文处理在经济上不划算。

认识认知瓶颈：即使拥有无限上下文，要求单个模型在数十个独立任务上保持质量，也会造成更多上下文无法解决的退化。把任务拆分给子代理（Subagent），而不是扩张上下文。

## 实用指南

### 四桶缓解框架

根据活跃的退化模式应用以下四种策略：

**Write（写入）**：用 scratchpad、文件系统或外部存储把上下文保存到窗口之外。当上下文利用率超过窗口的 70% 时使用。这让活跃上下文保持精简，同时通过工具调用保留信息访问能力。

**Select（选取）**：通过检索、过滤与优先级排序，只把相关上下文拉入窗口。当出现分心或混淆症状时使用。加载前先做相关性评分；低于阈值的内容一律排除，而不是全盘纳入。

**Compress（压缩）**：通过摘要、抽象与观察掩码（observation masking）在保留信息的同时减少 token。当上下文在增长但所有内容都相关时使用。用紧凑的结构化摘要替换冗长的工具输出；把重复出现的模式抽象为单一引用。

**Isolate（隔离）**：把上下文拆分到多个子代理或会话，防止任何单一上下文增长超过其退化阈值。当出现混淆或冲突症状、或任务彼此独立时使用。这是最激进的策略，但对复杂多任务系统往往最有效。

### 韧性架构模式

实现即时（just-in-time）上下文加载：只在当前推理步骤需要时检索信息，而非预先抢载。使用观察掩码在处理后将冗长的工具输出替换为紧凑引用。部署子代理架构，让每个 Agent 只持有与任务相关的上下文。在上下文超过模型特定的退化起点阈值之前触发压缩整理（compaction），而不是等症状出现之后。

## 示例

**示例 1：检测退化**
```yaml
# Context grows during long conversation
turn_1: 1000 tokens
turn_5: 8000 tokens
turn_10: 25000 tokens
turn_20: 60000 tokens (degradation begins)
turn_30: 90000 tokens (significant degradation)
```

**示例 2：缓解迷失在中部**
```markdown
# Organize context with critical info at edges

[CURRENT TASK]                      # At start
- Goal: Generate quarterly report
- Deadline: End of week

[DETAILED CONTEXT]                  # Middle (less attention)
- 50 pages of data
- Multiple analysis sections
- Supporting evidence

[KEY FINDINGS]                     # At end
- Revenue up 15%
- Costs down 8%
- Growth in Region A
```

**示例 3：上下文污染熔断器**
```text
symptom: agent keeps citing an incorrect retrieved claim after correction
diagnosis: poisoned context, not a missing-instruction problem
action:
  1. identify first turn where the bad claim entered
  2. truncate or restart from before that point
  3. reload only verified sources
  4. record the rejected claim and source provenance
```

**示例 4：上下文冲突标注**
```yaml
conflict:
  topic: billing API version
  source_a: docs/v1.md says endpoint is /charges
  source_b: docs/v2.md says endpoint is /payments
  precedence: docs/v2.md
  reason: current production version
```

## 准则

1. 在开发过程中监控上下文长度与性能的相关性
2. 把关键信息放在上下文的开头或结尾
3. 在退化变得严重之前实现压缩整理触发器
4. 检索到的文档加入上下文前先验证准确性
5. 使用版本管理防止过时信息引发冲突
6. 分割任务以防止跨目标的上下文混淆
7. 为优雅退化而设计，而不是假设完美条件
8. 用逐步增大的上下文测试以找到退化阈值

## 常见陷阱

1. **正常方差看起来像退化**：模型输出质量在多次运行间自然波动。不要凭单次质量下降诊断退化，而要在多次运行上建立基线，寻找与上下文增长相关联的持续、同步下滑。某一次 5-10% 的质量抖动是噪声；同样的抖动持续出现在 40K token 之后才是信号。

2. **模型特定阈值会过时**：基准表格中的退化起点数值反映的是特定模型版本。供应商更新、微调变更和基础设施变动都可能让阈值向任一方向移动 20-50%。每季度以及每次重大模型更新之后重新实测，不要把公开阈值当作永久不变。

3. **大海捞针（needle-in-haystack）分数制造虚假信心**：模型在大海捞针测试中得到 99%，不代表它在生产环境中能处理好 128K token。needle 测试度量的是从被动上下文中检索单一事实，而真实工作负载需要多事实推理、指令遵循以及跨整个窗口的综合。使用能反映真实工作负载模式的任务特定基准。

4. **相互矛盾的检索文档会无声地污染**：当 RAG 管线检索到两篇在某个事实上有分歧的文档时，模型可能无声地选择其中之一而不提示冲突。这看起来是正确回答，实际上是随机选择。在文档进入上下文之前，在检索层实现矛盾检测。

5. **提示词质量问题伪装成退化**：糟糕的提示词结构（含糊的指令、缺失的约束、不清的任务表述）产生的症状与上下文退化完全相同：输出不一致、无视指令、工具使用错误。在诊断退化之前，先验证同一提示词在低上下文长度下是否正常。如果它在 2K token 时就失败，问题在提示词，不在上下文。

6. **退化是非线性的，带悬崖**：性能不是渐进退化：它在模型特定阈值之前保持稳定，然后急剧下降。为"优雅退化"设计的系统常常错过这一模式，因为监控检查假设线性下降。把压缩整理触发器设在悬崖之前（已知起点的 70% 处），而不是起点本身。

7. **过度组织上下文可能适得其反**：直觉上，结构良好且连贯的上下文应该胜过杂乱内容。研究表明，对检索任务，打乱顺序的大海捞针堆有时胜过连贯版本，因为连贯上下文会制造错误关联。要针对具体任务测试重度结构化格式是否真的有效，不要想当然。

## 集成

本 Skill 负责对已发生的上下文失效进行诊断与缓解。一旦失效被识别，实现层面的战术由相邻 Skill 负责：

- `context-fundamentals`：在失效出现之前，对注意力与 context window 的概念性解释。
- `context-optimization`：诊断明确之后的掩码、缓存、分区等 token 效率战术。
- `context-compression`：当累积上下文必须被压缩整理时的结构化摘要与交接。
- `filesystem-context`：把原始输出、日志与草稿状态卸载出去，让被污染或臃肿的上下文无需留在提示词中即可被检查。
- `multi-agent-patterns`：把任务隔离到独立上下文以防止混淆与冲突。
- `evaluation`：退化测试与生产监控。
