# Check：发布前审查

在第一行开头内联加上 🥷，不要单独成段。

> 注意：`/review` 是 Anthropic 内置的 PR 审查插件命令。Waza 使用 `/check`（或别名 `code-review`）。不要在本 Skill 内部重新触发 `/review`。

读取 diff 并找出问题。审查、审计、分诊与就绪度请求仅输出报告；只有在本任务仍然有效的明确修复授权下才应用修复。完成意味着所请求的审查面已覆盖，且每一条验证声明都来自本次会话。

## 结果契约

- 结果：基于当前 diff、项目上下文与实时证据的审查结论、发布决策或维护者操作。
- 完成标准：给出发现、修复、发布状态或阻塞项时，附上能证明它们的命令、产物或远端状态。
- 证据：worktree 状态、diff、公开项目文档、manifest、CI、包内容、发布或 registry 状态，以及当前命令输出。
- 输出：先给出简洁的发现，然后（如适用）给出验证与发布状态摘要。多步骤或发布类运行，以及包含多项内容或截图的请求，都要以编号完成清单（done / 不适用 / 剩余）收尾，绝不能是让用户读完后还要问"是不是都做完了"的叙述。
- 授权：只读意图可以检查 worktree 与远端状态，但不得编辑文件、应用自动修复、commit、push、publish、评论、关闭、merge 或切换分支。每一次写操作或公开操作都需要当前请求的授权，或针对同一未完结任务仍然有效的授权：即点名了本操作与目标、且未被撤回的授权。后续回合询问进度或说"continue"既不撤回该授权，也不需要重复它。新的操作、更大的范围、变更的目标，或原授权未覆盖的风险，都需要各自的授权。批准草稿不等于批准 commit、push、publish 或删除。

## 持久上下文预检

何时涉及持久上下文，以及任何内容成为持久规则之前适用的脱敏关卡，见 [references/durable-context.md](references/durable-context.md)。

对 `/check` 而言：当前 diff、CI 与远端状态优先于记忆。持久记忆可以解释用户意图与偏好的后续动作，但公开项目规则仍来自 README 文件、manifest、CI workflow、发布文档以及当前会话中的明确指示。绝不要把私有记忆当作公开项目要求来引用。


## Worktree 安全预检

在任何审查、分诊、发布、release 或 PR 操作之前，先用以下命令读取当前 worktree：

```bash
git status --short --branch -uall
```

将已修改、已暂存和未跟踪的文件视为用户的工作成果。你可以读取它们并将其纳入审查面，但未经用户在当前回合明确批准，不得移动、隐藏、覆盖、清理或丢弃它们。

不要在默认审查或 PR 流程中运行这些命令：`git switch`、`git checkout`、`git reset --hard`、`git clean`、`git stash -u`、`git stash --include-untracked`、`git stash -a`、`git stash --all` 或 `gh pr checkout`。如果确实需要切换分支或清理，停下来并请求用户确认这一确切操作。

不要通过把未跟踪文件、生成文件、截图或本地临时文件移进 `/tmp` 或其他暂存目录来"保护"用户工作。把别人的 WIP 移出检出，与 stash 它属于同一类干扰。如果生成、打包或验证需要干净的树，应基于已知 commit 使用单独的 worktree，并只把你拥有的产物或补丁复制回当前检出。

检查 PR 时，优先使用不切换当前工作树的命令：`gh pr view`、`gh pr diff`、`git fetch origin pull/<n>/head:refs/tmp/pr-<n>` 与 `git merge-tree`。commit 与 push 的后续动作还要按 `references/mode-ship.md` 增加 HEAD 重读。

## 模式选择器

选择与用户意图匹配的模式，然后在行动前完整阅读它。各模式叠加在下方的共享审查面（审查范围、硬性规则、硬性叫停、自动修复、专项审查、验证、签收）之上，该审查面在所有模式下都适用。仅当某一行匹配时才加载对应模式文件；默认审查路径不需要加载任何模式文件。

| 用户意图 | 模式 |
|---|---|
| "implement this plan"、交接来的 `/think` 输出 | [计划执行](#plan-execution-mode) |
| diff 或 PR 就绪、"review"、"看看代码"、"合并前" | 默认审查（从[获取 diff](#get-the-diff)开始） |
| "look at issues"、"review PRs"、"triage"、"批量处理" | 加载 `references/mode-triage.md` |
| "is this worth a release"、"值不值得发版" | 加载 `references/mode-ship.md`（发布价值分析） |
| "commit"、"push"、"publish"、"release"、"close issue"、"发布表情" | 加载 `references/mode-ship.md`（发布上线后续动作） |
| "audit"、"项目体检"、"项目评分"、"给项目打分"、"深入分析项目代码"、"scorecard"、"linus review" | 加载 `references/mode-audit.md` |
| 文档、PDF、散文审查 | 委托给 `/write` 的文档审查模式，并入同一份完成清单；没有 `/write` 时，使用可用的散文审查能力并说明这一限制 |

进入任何模式之前，先运行[项目上下文提取](#project-context-extraction)，以及（若记忆在范围内）[持久上下文预检](#durable-context-preflight)。

## 项目上下文提取

这是 Waza 的公开、独立代码审查能力；它从不依赖私有机器路径或未公开的指令。从 diff 及其公开上下文（manifest、CI workflow、AGENTS/CLAUDE 文件、发布说明）中了解项目，直到掌握其验证命令、生成或受保护的文件、发布产物与领域风险。具体形态见 `references/project-context.md`。

- 当项目上下文与本 Skill 重叠且两者都能满足时，满足更严格的一方。项目的明确例外优先，且报告要指出这一点；更严格并不是推翻成文决定或重排宿主指令优先级的许可。
- 优先使用项目点名的验证命令，并阅读 workflow 本身而非描述它的那句话。文档声称 CI 强制执行某事只是一种说法；只在一侧（本地或 CI）运行的检查，在那侧绿了也说明不了另一侧的情况。

就发布就绪或公开发布而言，还要按 `references/project-context.md` 填写 Release Gate 2.0 矩阵。它涵盖审查基线、脏/暂存/未跟踪状态、最新 tag、origin 同步、版本字段、生成产物、包/归档内容、发布资产、registry/appcast/CI，以及公开 issue/PR 状态。矩阵证据缺失即阻塞"可以发布"的结论。仅 commit/push 的任务使用 `references/mode-ship.md` 中的源码交付检查；无关的发布资产与 registry 状态不在范围内。

## 计划执行模式

当消息以"Implement the following plan"、"按计划实施"、"按照计划"、"整"、"可以干"或"直接改"开头、后接计划正文，或链接到某个 `/think` 输出时激活。跳过代码审查：点名计划，检查 `git status --short --branch -uall` 是否存在使其不安全的漂移（指出冲突并停止），执行，然后运行项目的验证命令。

审查后发布：当 `AGENTS.md` 或当前会话要求"审查后提交"、"绿了就发"或类似内容时，在干净的审查或完成的计划之后加载 `references/mode-ship.md`，声明"继续发布"，并且不再重复询问。

## 获取 diff

从用户的措辞与当前仓库状态推导审查基线。当范围已经可以推断时，不要开口索要 commit：

- **全部本地或未提交改动**：盘点已暂存、未暂存与未跟踪文件，以及领先于所配置上游的本地 commit。处于基线分支并不使这一范围变得模糊。
- **PR 或分支审查**：使用 merge base 到被审查 head 的区间，再把该检出中的脏文件作为单独的审查面加入。
- **自上次发布以来**：使用最新已发布稳定 tag 到 `HEAD` 的区间，而不是本地版本字段，然后加入脏文件。
- **最近 N 天或显式 ref**：将该时间/ref 边界解析到 `HEAD`，然后加入脏文件。
- **已知良好或上一个可用版本**：比较该 ref 到 `HEAD`；只有当回归点本身未知时，才转 `/hunt` 的 Bisect 模式。
- **全项目审计**：使用审计模式，而不是假装某个 diff 就是整个仓库。

在审查前冻结已解析的基线、`HEAD`、worktree 盘点、生成/分发面与已委托的范围。只有当两个合理基线会实质改变结论时，才提出一个收窄的问题。如果审查中应用了修复或仓库状态发生变动，旧结论即失效：在签收前重读 `HEAD`、状态与完整解析后的 diff。

## 审查范围

测量 diff 并划分审查深度：

| 深度 | 标准 | 审查者 |
|-------|----------|-----------|
| **快速** | 少于 100 行，1-5 个文件 | 仅基础审查 |
| **标准** | 100-500 行，或 6-10 个文件 | 基础 + 按需专项 |
| **深入** | 500+ 行、10+ 个文件，或触及鉴权/支付/数据变更 | 基础 + 全部专项 + 对抗性检查 |

在继续之前先说明深度。

明确的深度措辞覆盖规模阈值。"All"、"全部"、"deep"、"深入"或"仔细"意味着对已解析盘点的全范围覆盖，即使文本 diff 很小；它不允许跳过未跟踪文件、生成镜像、必需产物或待执行的审查者。

纯内容 diff 即使触及多个生成文件也可以保持快速：版本字符串、日期、发布文案镜像、sitemap 日期或一一对应的本地化文案改动，通常只需要逐行回读加 grep 一致性检查，而不需要专项审查编队。只有当 diff 改变了逻辑、生成规则、公开分发行为或超出字面文本替换的用户可见语义时才升级。

## 我们做的是被要求的事吗？

在读代码之前，先检查范围漂移：diff 与所述目标是否匹配？标注：**on target（切题）** / **drift（漂移）** / **incomplete（未完成）**。

每一个变更文件和新的公开面都必须能用一句话追溯到所述目标；无法追溯的文件、依赖、配置开关、抽象、生成产物、workflow 权限或发布行为都是漂移，除非证明其必要。以下任意一条即足够：与目标无关的文件，修复或功能内部的纯重构或无关删除，未提及的依赖或辅助模块，或者悄悄添加用户可见 UI、默认配置、workflow 权限或发布行为的清理。对每一个新的公开设置、flag、环境变量、命令或服务，要问谁会改动它、为什么没有一个正确的默认值就能满足他们；没有证据表明存在用户分群时，把该开关视为漂移，改为修好默认路径。

每次审查都主动运行一次过度设计检查：对每个新文件、选项、回退、层或抽象，问"如果去掉它，这个改动是否仍然成立"，并把所有去掉后仍然成立的项报告为可移除。

## 质疑路线，而不只是 diff

范围漂移检查的是 diff 对所述目标；这一节检查的是目标对路线。当用户宣布路线已定，或仓库的设计文档已记录该决定时跳过——不要重新争论刻意做出的取舍。

当发现聚集在同一个根因上——同一类 bug 被反复打补丁、由架构本身引出的权限或状态问题、把简单问题做复杂了——停止罗列补丁，先给出路线结论：保留 / 调整 / 更换 / 信息不足。只有当某个真实替代方案能以可接受的迁移成本消灭该问题类别时，才比较它；绝不为填满报告而编造替代方案。结论出来之前不给补丁清单。

## 模式修复完备性

当 diff 修复了某类 bug 的一个实例时，在仓库中 grep 相同形态（hunt 的 Scope Blast 模式），并确认其他实例已被处理。列出任何未清扫的同类：携带相同风险的列为硬性叫停，风险较低的列为建议。

当 diff 包含反复出现或难以观测的 bug、捕获输出或异步完成、简化或删除、对历史敏感的归一化、对用户文件的非原子替换、宽泛的破坏性匹配器、重复推导、测试面保真度、从未上线的迁移或未知标识符时，加载 `references/review-patterns.md` 的对应小节。与 diff 无关时不要加载该目录。

## 命令与安装面

当 diff 触及 CLI 入口、安装器、配置/环境变量处理或变更型命令（清理、更新、卸载、迁移、缓存清除）时，处理 `references/release-surfaces.md` 的 CLI 命令面小节；当它触及 skill、plugin、marketplace 条目、包 manifest、生成镜像或已发布归档时，处理其打包安装面小节。两者背后的教训：库测试与 manifest JSON 永远证明不了已安装运行时的行为，且每个变更型命令都是一个安全汇点。终端输出也是被渲染的面；改动面向 CLI 的文本或布局后，重新运行命令并读取真实输出。

## 硬性规则

- **不得有未经验证的声明。** 除非 shell 输出就在本回合的记录里，否则不要写"我验证了 X"、"我运行了 Y"、"测试通过"或"这修复了 Z"。如果你是靠阅读代码推理行为，就说"基于阅读代码"，而不是"我验证过"。签收中的每一条验证声明都必须指向本会话中真实运行过的命令，或者标注为复用证据并写明其来源 commit 与输入，以及为确认它仍然适用而重新检查了什么。项目允许的复用没问题；把它当成本次会话的运行来呈现不行。
- **重读事实性来源。** 在引用或发布之前，在本回合内刷新行号、worktree 状态、回退行为、locale 覆盖、产物状态，以及任何 issue、PR 或会话线程的身份。早先的上下文与审查者备注只是线索，不是证据。
- **公开回复**：正文遵循 `/write` 的公开回复模式；发布、编辑、回读与收尾遵循 `references/public-reply.md`。

## 硬性叫停（合并前必须修复）

以下只是示例，并不穷尽——任何未审查即合并就可能造成不可逆损害的 diff 都要标注。

- **破坏性自动执行**：任何标记为"safe"或"auto-run"、会修改用户可见状态（历史文件、配置、偏好、已安装软件）的任务，都必须要求明确确认。
- **源码与分发不同步**：源码改动所隐含的全部下游内容都必须在宣告完成之前重新生成、跟踪、上传并保持版本一致：重新构建并纳入生成或打包的输出，发布说明或 workflow 中点名的每个产物都已实际上传，每个新的辅助模块、引用文件或脚本都在构建出的归档中，且版本字段在 manifest、包元数据、changelog、tag 与 lockfile 之间同步。
- **验证器失败层级不明**：如果验证器在断言之前失败，或因缺少可选依赖、引导噪音、构建服务瞬时崩溃、模拟器不可用或工具配置问题而失败，要区分环境配置失败与产品失败。只有在有新证据或更窄的环境时才重试。在预期的测试主体或产物检查真正运行过之前，不要断言仓库坏了。反过来的情况是同一种叫停：没有运行真实路径就通过的验证器——一个跳过了可选依赖却仍然打印 OK 的 job，一个提前返回、输出为空、使"空即为真"断言通过的函数，一个报告已修复却从未打开过的渲染——都是虚假的绿。只有当至少一个未跳过、非空白的用例真正走过了该路径，且断言对空白会失败时，通过才算数。
- **带着自己未解决的发现去发布**：当同一次运行先产生了审查发现、随后进入发布动作时，每一条发现都必须已修复，或重述为"已知，仍要发布"并写明其用户影响且获确认，然后才能继续发布。既有的发布授权不覆盖在其给出之后才发现的问题。
- **注入与校验**：系统入口点的 SQL、命令、路径注入。凭据被硬编码、记录日志、提交或复制进公开文档。
- **依赖变更**：package.json、Cargo.toml、go.mod、requirements.txt 中出现意外的添加或版本升级。标记任何并非明显为 diff 所需的新依赖。反方向也是发现：仓库内零引用的已声明依赖或已链接 SDK 要提请维护者注意，而不是被悄悄移除（它可能为即将到来的功能预备，且未使用的统计/遥测 SDK 仍会拖累应用审查与隐私 manifest）。移除需要维护者在当前回合的同意、先有证明零引用的 grep、之后再完整构建一次。涉及 lockfile、自动化安全 PR 或版本钉死时，加载 `references/review-patterns.md`（依赖变更）。
- **安全汇点**：破坏性文件操作、shell 或 AppleScript 构造、cwd/路径/符号链接穿越、审批或沙箱边界变更、签名/appcast 流程以及鉴权提示，都需要对校验、回滚与用户确认行为做显式审查。

## 发现质量闸门

每一条发现都需要确切的 file:line、触发坏结果的具体输入或状态、对上游调用方与下游消费方的阅读（而非孤立地看这个函数），以及一个资深审查者在真实 PR 中会在此严重度上提出的等级；缺任何一项，就丢弃它或降级为建议。在把一个变更称为回归之前，先读它的 commit 信息与作者意图：维护者的刻意变更是决定，不是发现。模糊的发现会训练读者忽略真正重要的发现。

**干净的审查也是有效的审查。** 不要为了证明本次调用合理而制造发现。在说明了审查面的前提下，零发现就是完整的输出。用低置信度的噪音给报告注水，比什么都不报更糟。

**HIGH 与 CRITICAL** 还需要说明为什么现有防线（校验、类型系统、上游捕获、框架默认值）没有已经阻止它。展示不出来？降级为 MEDIUM，或丢弃。"这*在某些条件下*可能会坏"不构成 HIGH。

## 知识同步

如果 diff 引入了项目文档尚未承载的不变式（安全闸门、UI 约束、发布步骤、跨文件同步要求），它应进入所有目标运行时都会读到的、最窄的受跟踪指引，通常是 AGENTS.md。diff 里的审查报告或评分卡是证据，不是持久文档：提取其稳定规则，而不是提交快照。明确的文档更新按 `safe_auto` 应用，或标记为 `doc debt`；没有新内容时，签收写 `doc debt: none`。

## 专项审查（仅标准与深入）

加载 `references/persona-catalog.md` 了解激活方式、并行或顺序审查以及发现验证。

在给出全范围结论之前，为每个已委托的审查对账一份完成清单：分配的范围、返回的状态与未覆盖的剩余部分。等待每个活跃的审查者完成，否则把其范围标注为未审查。只要还有审查者或必需验证未完成，绝不说"都读完了"、"审计全部完成"或"没有问题"。

## 自动修复路由

| 类别 | 定义 | 动作 |
|-------|------------|--------|
| `safe_auto` | 无歧义、无风险：错别字、缺失导入、风格不一致 | 仅在明确的写授权之后应用；否则报告 |
| `gated_auto` | 有明确预期结果的行为修复：null 检查、错误处理补充 | 在明确修复授权内应用；只在需要扩大范围或存在未决的用户选择时才询问 |
| `manual` | 没有既定预期结果的架构或安全权衡 | 从项目上下文中解决；呈现剩余的用户决策 |
| `advisory` | 仅信息性 | 在签收中注明 |

写授权覆盖其范围内的必要修复，包括达到所请求结果所需的行为变更。路由类别不会制造额外的审批步骤。仅报告模式下不得修改 worktree。

审查期间做出的任何修复都会使修复前的结论失效。重新冻结基线、重跑暴露该发现的检查、刷新同类清扫，并完成审查深度所要求的最终对抗性检查，然后才能宣告就绪。

## 对抗性检查（仅深入）

运行 `references/persona-catalog.md` 中的四个攻击角度。来自独立角度的收敛会提高置信度；孤立发现要面对与专项结论相同的逐发现怀疑者验证。压制置信度低于 0.60 的发现。

## 平台操作

从公开项目文档推导宿主的 CLI/API；不要把 GitHub 命令强加给其他宿主，merge 前确认 CI 通过。以结构化状态轮询 CI，而不是流式文本：`gh run view <id> --json status,conclusion`（或宿主的等价命令）。把 `gh run watch`、测试输出或构建输出通过 `tail`/`head` 管道会吞掉真实退出码，可能把失败或仍在运行的 run 报告为绿。

## 验证

使用与变更面相称的项目已知验证命令。否则，从目标项目根目录运行 `bash <skill-base-dir>/scripts/run-tests.sh` 可以发现候选命令。报告退出状态与摘要，附相关失败输出而非完整的通过日志。

检查失败需要诊断；未发现可用命令是发现能力的缺口，不是失败或没有验证面的证明。检查项目文档、manifest 与 CI 以找到合适的检查。没有可用检查时，以明确的证据限制完成只读审查。只有在必需证据缺失或失败时才阻塞修复或就绪声明，且只有当无法从项目上下文中恢复命令时才开口索要。

对于 bug 修复：必须在修复完成之前存在一个在旧代码上会失败的回归测试，并在该代码上跑出红（hunt 的回归守卫规则）。要独立于实现建立预期行为：更新快照不能证明快照正确。对 agent 指令而言，关键词检查只能证明文本被记住；行为检查要审视工具动作及其产生的文件或产物，包括被禁止的副作用。在依赖新的检查器之前，先各跑一个已知良好与已知糟糕的用例，并在相同运行时与输入下比较基线与候选。

在脏的或多 agent 的检出中，本地构建或测试通过不能证明你的改动是健全的：树中已有的无关 WIP 可能补上缺失的符号、掩盖一次破坏，或因与你无关的原因失败。要在隔离环境中验证——`git worktree add --detach <known-good-commit>`，只 `git apply` 你拥有的文件的 diff，然后在其中构建/测试。干净的隔离通过才是真信号；被污染的本地通过不是。

## 易踩的坑

| 发生了什么 | 规则 |
|---|---|
| 新文件名重复了某个 locale、平台或后缀约定 | 创建或重命名文件前，先检查目标目录既有的命名约定 |
| 未做 provider 运行时或环境变量检查就部署 | 遵循项目的公开部署文档，并将 provider 配置与本地必需的环境变量及运行时设置比对 |

## 签收

在任何表格或细节之前，用普通散文在最终消息开头给出 `status` 行：准确说明工作此刻所处的位置，附 hash、tag 或阻塞项。埋在验证表格之下的结论读起来像没做完；表格支撑结论，但不取代结论。

```
status:           [committed and pushed as <hash> / staged, not committed / released vX.Y.Z / blocked on <what>]
files changed:    N (+X -Y)
scope:            on target / drift: [what] / removable: [what]
user-visible delta: none / [entry, UI, copy, behavior added, removed, or changed]
review depth:     quick / standard / deep
hard stops:       N found, N fixed, N deferred
sibling sweep:    N same-shape sites checked, N fixed / none found / not applicable
specialists:      [security, architecture] or none
new tests:        N
public actions:   replied #N, closed #N, reactions done / none pending
doc debt:         none / AGENTS.md needs X / rules need Y
verification:     [command] -> pass / fail
```

`public actions` 列出任务隐含的每一个对外步骤（issue 回复、关闭、发布表情）及其完成或待办状态；一个需要用户开口追问的外部操作就是没有完成。

对全范围或修复后的结论，`scope` 由冻结的基线与当前盘点支撑，而不是由最后看的那个补丁支撑。对发布动作而言，status 行在每一个当前已授权的清单项都处于 `done`、`not applicable` 或带证据的 `blocked` 之前都不算完整。

写过文件的回合要以 `git status --short --branch` 的真实输出收尾，若执行过 push，还要附该 sha 对应 CI run 的 `status,conclusion`；如果哪个命令没有运行过，第一行要说明是哪一个。
