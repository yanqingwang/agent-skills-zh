# Hunt：先诊断，再修复

在你的第一行开头内联加上 🥷，不要让它单独成段。

针对症状打的补丁，会在别处制造新的 bug。

## 结果契约

- 结果：在任何修复实施之前，根因已被识别。
- 完成标准：一句话解释成因，每一个被观察到的症状都能被它覆盖，且修复或移交已通过可复现的检查得到验证。
- 证据：源码追踪、复现命令或 UI 路径、日志或状态、针对性的测试/构建输出，以及 UI 或原生缺陷的运行时证据。
- 输出：根因、修复或移交、验证结果，以及任何尚未排查的同类风险。
- 授权："diagnose"、"investigate"、"why"、"look into"、"排查"、"看看"或等价表述仅为报告。只有当当前请求明确要求修复、变更、实现或优化时，或针对同一未完成任务、动作/范围/目标均未变的修复授权仍在生效时，才实施修复；即便如此，仍须先完成根因证明。修复授权绝不附带 commit、push、发布或任何破坏性操作。

**在你能用一句话陈述根因之前，不要碰代码：**
> “我相信根因是 [X]，因为 [证据]。”

指明具体的文件、函数、行号或条件。“状态管理有问题”不可检验。“`useUser` 在 `src/hooks/user.ts:42` 处缓存过期，因为依赖数组缺少 `userId`”才可检验。如果你达不到这个具体程度，说明你还没有假设。

## 诊断信号

假设质量门：假设必须解释每一个可观察到的症状，而不只是最先报告的那一个；只覆盖一部分，那是症状层面的猜测，不是根因。报告者一笔带过说“不相关”的症状，同样是假设必须覆盖的症状。对时序相关的问题（闪烁、偶发失败、竞态），先稳定复现，再诊断。

合理化的气味：“我就试试这个” = 没有假设，先把它写出来。“我很有把握” = 去跑能证明它的手段。“大概是同一个问题” = 从头重读执行路径。“在我机器上是好的” = 先列举环境差异再下结论。“再重启一次” = 逐字读最后一条错误；没有新证据，重启永远不要超过两次。

## 持久上下文预检

持久上下文何时在范围内、以及其中任何内容沉淀为持久规则之前适用的脱敏门，见 [references/durable-context.md](references/durable-context.md)。

对 `/hunt` 而言：持久上下文只是假设的燃料，当前代码、日志和复现证据一律优先于记忆。它永远不能替代一句新写的根因陈述，也不能替代可复现的症状清单。

## 二分定位模式（Bisect）

触发条件：用户说“以前是好的”“之前是好的”"used to work"“上一次提交还是对的”"broke after update"，或记得某个具体的好 commit 或版本。

- 先保护用户的 worktree：`git status --short --branch -uall`。存在任何已修改、已暂存或未跟踪的文件，就意味着不能在当前 checkout 里做 bisect：改在临时 detached worktree 中运行，结束时删除该 worktree。如果临时 worktree 不可行，停下来，请求明确的清理/stash 批准。
- 如果上一个正常版本只往前几个版本，先 `git diff <last-good>..HEAD -- <suspect path>` 并阅读这段差异。回归通常在那里直接可见，代价只是 bisect 的零头；只有当差异过大或元凶不明显时，才退而做 bisect。
- 只用预先定义好的非交互式 pass/fail 命令做 bisect，并把记账交给 git（`git bisect good/bad`），直接测试可疑 commit 时也一样。当它指认出元凶，只读那一次 diff 并追到具体行，然后在删除临时 worktree 之前运行 `git bisect reset`。

## 反复回归 / 截图参照模式

触发条件：用户说同一问题修复后仍然不对、提供了一张“好的”截图/版本/文件，或描述某个视觉结果以前是对的。

把参照物当证据，不当装饰：用用户的具体措辞列出每一个被报告的和可见的症状；确定参照基准（reference oracle：上一个正常的 commit、旧构建、fixture、截图、所描述的期望状态）；在动手改之前先定义 pass/fail 检查；然后指明当前与参照之间的确切差异。当证据指向渲染损坏、竞态、字体管线或状态路径时，不要把视觉缺陷泛化成“样式打磨”。

如果问题纯属主观的 UI 品味，转给 `/ui`。如果属于渲染、状态、时序、构建产物、字体生成，或相对某个已知正常版本的回归，留在 `/hunt`。

## 波及面排查模式（Scope Blast）

触发时机：修复完一个根因模式之后、宣布 bug 完成之前；以及用户说“举一反三”“举一反三深入看看”或“其他地方有没有同样问题”时。同样的形态常常还藏在另外 N 处；一个无视波及面的局部修复，会让代码树里留下 N - 1 个 bug。

提取模式特征（产生该 bug 的具体函数、正则、API 调用、CSS 选择器、锁获取、被跳过的校验或输入边界），并用 `grep -rn` 在整个仓库搜索，排除生成目录、构建产物和 vendored 依赖；对于“某一类 bug”的模式（如“任何漏加锁的 handler”），要按周边形态搜索，而不只搜字面文本。对每一处匹配，书面作答：同一个 bug / 可以不动（为什么）/ 不确定（问用户）。不得默默跳过任何匹配，也不得在波及面报告进入 Output 块之前声称“已修复”。排查中带出的无关 bug 只列出、不在本次 PR 中顺手修，除非用户同意。

## 证实或放弃

运行那一个“如果假设错了它就会失败”的探针，然后读结果。如果证据与假设矛盾，就彻底丢弃该假设，围绕探针刚刚显示的内容重新定向。不要把修复叠加在被证伪的假设上，也不要只因代码“看起来像”成因就保留假设。

## 运行时证据阶梯

在宣称 bug 已修复之前，先爬完这道阶梯：

1. 源码追踪：指名能产生该症状的确切函数、状态转换、文件、行号或条件。
2. 确定性复现：运行或编写出能产生该症状的最小命令、fixture、UI 路径或场景。
3. 日志/状态/缓存：检查能证明路径确实被走到的运行时状态，包括队列、数据库行、缓存、临时文件、生成产物或外部工具日志。
4. 构建/测试：运行能覆盖该修复的最小范围的测试或构建。
5. 真实运行时检查：对 UI、原生应用、浏览器、渲染或视觉类 bug，打开应用/页面/产物，用截图或具体清单验证可见结果。

对 UI、原生应用、视觉、渲染或生成产物类 bug，只编译通过并不够。如果环境中无法做运行时检查，说明原因，并把需要验证的确切界面、命令或产物移交给对方。

当缺的那一级正是报告者的环境、且本地无法复现时，下一个产物是对方可以粘贴运行的只读探针，而不是又一个假设。让它打印环境信息、有争议的度量值，以及假设所依赖的那部分状态，且不输出任何可能夹带秘密或私有路径的内容。不要预设你自己的环境布局：对方的安装方式、目录约定、locale、shell 和版本都不同，所以要探测发现，而不是硬编码。以可直接复制的纯文本交付：一条可运行的命令，加一块可贴回的输出。

对反复出现的同类失败，在打第二个修复之前，先加载 `references/failure-patterns.md`。

## 原生应用卡死模式（Native App Freeze）

针对沙滩球（beachball）、无响应、切换标签页冻结、首次打开迟滞、空闲唤醒停滞、悬浮层卡死或应用冻结截图，在改动代码之前先加载 `references/logging-techniques.md`（Native App Freeze Mode）。

## 定向日志

每条日志都是一个是非题：“如果在 Y 之前打印了 X，假设 A 存活；否则 A 出局。”不能证实也不能证伪任何假设的日志就是噪音。收尾前移除临时日志；常驻诊断挂到项目的 debug 开关之后。如果加一条日志就改变了行为，这本身就是时序、生命周期或并发问题的证据。完整手册见 `references/logging-techniques.md`。

## 渲染 bug 模式

针对 PDF 输出、分页、字体渲染或打印版式缺陷，加载 `references/rendering-debug.md`；其中包含激活触发条件与诊断清单（WeasyPrint 怪癖、字体加载、页面溢出、浏览器打印 CSS）。

## IME / Unicode 问题

针对输入法、字符渲染或文本编码类 bug（IME 状态、光标漂移、emoji 拆分、组合事件），在形成假设之前先查 `references/ime-unicode.md`。

## 硬性规则

- **修复之后症状依旧，是硬性停止；“让我再试一下”也是。** 两者都说明假设还没完成。再次碰代码之前，从头重读执行路径。
- **三个假设都失败后，停下来。** 用下面的移交格式呈现检查过什么、排除了什么、还有什么未知。询问如何继续。
- **外部工具失败：先诊断再换。** 当 MCP 工具或 API 失败时，先查明原因（服务在跑吗？API key 有效吗？配置对吗？），再尝试替代方案。
- **系统/工具链症状需要更低层的基线。** 在归咎于看得见的应用、生成文件或顶层功能之前，先测量更底层的原始数据：OS 采集对比后处理、运行时服务对比 UI、编译器/工具链对比测试断言、网络/API 对比客户端处理。被基线证伪的假设就淘汰掉，不要反复兜圈。
- **视觉/渲染 bug：先做静态分析。** 在加 console.log 或可视化调试覆盖层之前，先在 DevTools 中追踪绘制层、层叠上下文和层级顺序。日志捕捉不到合成器（compositor）做的事。只有静态分析失败之后才加插桩。
- **行为/生命周期/异步 bug：形成假设的同时加插桩。** 窗口生命周期、事件投递、导航、焦点、定时器、状态机和异步顺序类 bug 几乎从来不是单靠静态阅读就能解决的。一旦假设涉及“这个回调比那个先/后触发”“Y 运行时这个状态应该是 X”“这个对象在这里应该仍然存活”，就先加日志再写任何修复；连续猜两次就是硬性停止信号。合成器行为需要 DevTools 而非日志；纯逻辑 bug（公式错误、差一错误）只需静态分析。
- **魔法数字调过第三轮：停下，统一。** 当一个间距/尺寸/阈值被调整了三次看起来仍不对，bug 是结构性的，不是数值性的。把 N 个各自独立的值换成一个具名 token（`Spacing.s4`、`--gap-content` 等），并验证这种不对称是不是在掩盖一个缺失的约束。调参之后依然存在的不对称是结构性的；继续调不会收敛。
- **性能抱怨需要数字。** 对 Native App Freeze Mode 之外的“慢”“卡”“内存增长”类报告，先测基线（墙上时钟耗时、profile 采样、内存占用），修复，然后重测并报告前后数字。“感觉变快了”不是证据。
- **在授权范围内修复成因。** 继续完成必要的修复，包括前置性重构（例如共享接口变更），只要你说明了它为何必要；只有当修复会扩大该范围、或需要未决的行为取舍时才发问，且单凭文件数量不构成批准边界。不相关的重构分开处理；诊断完成后，明确要求的功能走它自己的工作流、记在同一份完成台账下；仅有 bug 修复授权并不意味着授权实现未被要求的功能。

## 易踩的坑

| 发生了什么 | 规则 |
|---------------|------|
| 给重复界面的另一份副本打了补丁 | 动任何文件之前，先沿执行路径反向追溯到真正渲染的那个实例 |
| 编排器报告 RUNNING，而下游阶段配置有误 | 多阶段流水线中，逐阶段隔离测试 |
| 竞态条件被误诊为状态过期 bug | 对时序敏感的问题，先查事件时间戳与顺序，再看状态 |
| 本地能复现，CI 里却失败 | 先对齐环境（运行时版本、环境变量、时区），再追代码 |
| 从应用内启动正常，经文件关联 / 拖放 / 深链 / 外部代理打开就坏 | 用用户描述的确切入口点复现。应用内初始化与“带文件冷启动”的初始化不同；文档到达时状态可能尚未就绪。 |
| 修复匹配了报告者的环境，但对其他所有人毫无变化，或使默认行为回归 | 缺陷报告是证据，不是全部范围。说明这个修复改变的是所有用户的默认体验，还是仅报告者的配置；优先修默认路径。 |
| 切换主题 / 模式 / 语言后出错，重启后恢复 | 状态没有在切换路径上重新应用。先追踪切换时的重算或失效路径；状态路径没修好前，不要逐像素调样式。 |
| 改了算法，输出依旧错误 | 读取方命中的可能是旧代码写下的持久化输出（扫描结果、分析缓存、带 TTL 的快照）。修改“先生成、后持久化”的数据，必须在同一次变更中让旧缓存失效或升版本；重新诊断之前，先确认运行时读的不是过期数据。 |
| 修好了能复现的那个原因并发布上线，同一个闸门又因别的原因拦住了下一个用户 | 会拒绝的闸门背后是一组原因，不是一个。发布之前枚举每一个可能拒绝的分支，并给每个分支一个可区分的错误码、一行原因和一条下一步命令。 |
| 用户的观察与日志不一致，最后信了日志 | 相信观察，把差异当作一条未插桩的路径。在正常路径上通过的探针说明不了失败路径的任何事；无法复现的探针是无效探针，不等于缺陷不存在。 |
| 在一个从未提供该能力的运行面上修补受能力门槛限制的功能 | 写修复之前，先确认运行面（模拟器、真机、沙箱、受限 entitlement）支持该能力。不支持就说明并停止；任何源码改动都变不出这个能力。 |

## 输出

### 成功格式

收尾的第一行用一句平实的话说明结果、以及变更是否已 commit；下面的代码块为这句话提供支撑，不能替代它。

```
Root cause:        [what was wrong, file:line]
Fix:               [what changed, file:line]
Sibling sweep:     [N same-shape sites checked, N fixed / none found / not run, why]
Confirmed:         [evidence or test that proves the fix]
Tests:             [pass/fail count, regression test location]
Regression guard:  [test file:line] or [none, reason]
```

状态：**已解决**、**已解决但有保留**（写明保留点）或**受阻**（写明未知事项）。

**回归防线规则**：对任何复发过的、或曾被“修复”过的 bug，以下条件满足之前不算修完：
1. 存在一个回归测试：它在未修复的代码上失败，在修复后的代码上通过。
2. 该测试位于项目的测试套件中，而不是临时文件。
3. commit 信息说明了 bug 为何复发、以及这个修复为何能阻止它再次发生。
4. 红-绿是**真正跑过**的，不是想当然：先在隔离的临时 checkout 或 fixture 中对未修复代码运行新测试，再对修复后的代码运行。为这个对比不要 revert 或 stash 共享的 worktree。一个只被观察到“通过”的回归测试什么都钉不住。在输出中写明红的那次运行。有两种形态会让它无声地失败：其一，某些框架或语法下，测试中途的断言失败不会让整个测试失败，于是只有最后一个断言起门槛作用（在 shell 套件里这可能完全取决于括号写法，一个关键字被吞、另一个被捕获，所以要跑一个两行的最小复现来确认是哪种，而不是靠推理）；其二，断言某个错误字符串“不存在”，这种断言永远通过，因为任何代码版本都从未输出过那个字符串。任何否定式断言（“输出不得包含 X”）还需要同一测试中配对的正向用例，证明该断言确实可能失败。

### 移交格式（3 个假设失败之后）

状态标 **blocked**，然后给出：一句话的症状；每个假设及其检验方法、被排除的原因；已收集的证据（日志或堆栈摘录、复现步骤、版本、配置、运行环境）；仍未知或缺失的内容；以及下一步，指明用户需要提供哪些工具、权限或上下文。
