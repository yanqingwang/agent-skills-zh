# 安全审计

找出违反真实信任边界的漏洞，然后向所有者提供源码证据、安全的复现方式、优先级与最小有效修复。这是一套防御性的、以源码为准的工作流。没有具体受影响主体、资源或安全后果的候选，不构成已确认的发现项。

## 运行模式

本 Skill 默认仅提供指导。加载本 Skill 并不等于授权运行完整审计工作流或创建文件。

- **指导模式**：针对安全问题、聚焦式审查、方法论、问题分诊或对具体发现项的调查，只使用本 Skill 的相关部分。不要自动运行全部六个阶段，也不要创建输出目录或写入审计产物。可以在有用时启动聚焦的 Agent；它们会把结果返回给当前任务。
- **完整审计模式**：当用户明确要求审计或渗透测试某个代码库、要求完整、全面或端到端的安全审查，或要求报告产物时，使用完整工作流。运行全部六个阶段，并写入下文定义的文件。

如果请求两种模式都说得通，先提出一个聚焦的问题，再创建文件或启动完整工作流。

## 平台术语

本 Skill 与具体 Agent 平台无关：

- **Parent** 是协调本次运行并持有共享状态的 Agent。
- **Task tool** 是平台提供的委派或子代理机制。
- **`research` Agent** 是受委派、负责聚焦源码探索与事实核验的 Agent。
- **`general` Agent** 是受委派、负责大范围调查与有界本地执行的 Agent。
- 标题中的 **`subagent_type:`** 指明该工作由这两个受委派 Agent 角色中的哪一个执行。

在保留角色、写隔离、提示词与独立性边界的前提下，使用等价的平台能力。

## 通用执行安全

以下规则在两种运行模式下都适用。源码检查是只读的。目标控制的构建、测试、进程、浏览器、模拟器、fuzzer 与 fixture 处理，只能在一个同时提供以下全部控制的、由操作系统强制的沙箱内运行：

- 无外部网络；当检查需要本地客户端/服务端流量时，只使用隔离的 loopback 命名空间；
- 空环境，仅由显式允许列表中的安全值填充，并使用 scratch 本地的 `HOME`、临时目录与缓存；
- 目标与工具链只读，目标控制的进程只能在其被分配的 `scratch/` 目录内写入；以及
- 显式的低 CPU、内存、进程数、文件大小、磁盘与墙钟时间限制。

在目标控制进程之外，当构建必须在源码旁写入时，Agent 可以在被分配的 `scratch/` 目录中制作一份一次性的源码副本。在指导模式下，不得保留目标控制的文件。在完整审计模式下，只有可信的父侧代码可以按"写隔离"一节的流程，把最小的非机密结果提升到保留的 `artifacts/`。绝不向目标代码暴露保留的输出目录（Agent 自己被分配的 `scratch/` 除外）、其他 Agent 的目录、宿主主目录、凭据、套接字或共享服务。不得安装依赖，也不得让构建拉取依赖；只使用本地已有的工具与依赖。如果上述控制无法全部强制执行，就不要执行目标代码：把缺失的沙箱能力作为 needs-validation 阻塞项上报，并给出安全的校验计划。

使用虚构的主体、fixture 与假密钥。不得探测已部署的端点、外部服务、共享基础设施、生产环境身份、其他用户的数据或真实运行的控制平面。不得针对真实运行或共享的进程测试可用性，不得发布产物、改动发布版本、消耗付费 API 配额，也不得在确立缺陷所需的最小本地影响之外继续行动。如果决定性事实在源码或沙箱化 fixture 之外，将其作为待校验事项上报。

## 完整审计设置

在完整审计模式下，先在侦察之前确定以下取值：

- **Skill 目录**：包含本 `SKILL.md` 的绝对目录。
- **目标**：被审查仓库的绝对根路径。
- **仓库名**：来自目录名或本地 Git remote 的稳定仓库标识。
- **输出目录**：目标之外的一个新的可写目录，默认为 `~/security-audit-skill/<repo-name>/run-<N>`，其中 `<N>` 是下一个未使用的整数。仅当用户明确选定目标内部目录，且 Parent 确认版本控制忽略了整个目录时，才可使用目标内部目录；否则停止并要求提供外部路径。
- **源码引用**：被审查的 commit，以及 worktree 是否有未提交改动。不得把未经审查的生成文件或修改文件当作另一个修订版本。

### 写隔离

由 Parent 创建共享运行文件，且 Parent 是唯一写入者：

- `run-metadata.json`
- `architecture.md`
- `coverage-ledger.json`
- `findings.json`
- `REPORT.md`
- `FINDINGS-DETAIL.md`
- `NEEDS-VALIDATION.md`

每个猎手或验证者都会获得 `<output-dir>/agents/<agent-id>/` 下唯一的一个根目录，内含相互独立的 `scratch/` 与 `artifacts/` 目录。规范的 Agent ID 须匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`，且不得等于 Windows 设备名，例如 `con`、`prn`、`aux`、`nul`、`com1` 至 `com9`，或 `lpt1` 至 `lpt9`。小写 ID 可避免大小写折叠冲突。该 Agent 与每个目标控制的进程只能写入 `scratch/`；保留的 `artifacts/` 归 Parent 所有，绝不暴露给沙箱，且只能由可信的父侧提升代码写入。Agent 不得改动共享文件、目标源码、保留产物或其他 Agent 的目录。不得把 `/tmp` 或宿主主目录用作可写回退位置。

执行前，Parent 为该 Agent 的 `scratch/` 与 `artifacts/` 根目录打开并持有可信、不可继承的目录描述符，并记录一份允许列表，列出预期的、相对 scratch 的产物文件，以及显式的单文件与累计字节上限。绝不把这些描述符交给 Agent 或沙箱。在沙箱及其所有进程终止后，由可信的父侧代码逐个提升允许列表内的文件：

1. 校验声明的相对路径：拒绝绝对路径、空组件、`.`、`..` 或含符号链接的组件。
2. 从保留的 scratch 根目录描述符出发，以 no-follow 的目录相对操作逐级遍历每个父组件；绝不按路径重新打开。
3. 以 no-follow 与非阻塞方式打开叶子节点。
4. 用 `fstat` 确认它是普通文件、链接数恰好为 1，且处于记录的单文件与累计字节上限之内。
5. 从该描述符读取时再次强制执行这些上限。
6. 精确复制已校验的大小，再次执行 `fstat`，只要标识、类型、链接数或大小发生变化即拒绝。
7. 对目标位置，从保留的 artifacts 根目录描述符出发，以 no-follow 的目录相对操作逐级遍历每个父组件；要求每个已存在的组件都是真实目录，并以独占方式创建缺失的目录，然后重新打开并按 no-follow 校验。
8. 以不跟随链接的方式独占创建叶子文件，确认打开的目标是链接数恰好为 1 的普通文件，然后从已校验的源描述符复制，且不重新打开任何一条路径。
9. 在非 POSIX 系统上使用等价的竞态安全 API。
10. 绝不递归复制或通配（glob）scratch，绝不向 artifacts 解压档案，也绝不打开或提升符号链接、FIFO、套接字、设备、目录、硬链接文件、仍在变化的文件，或超出其限额的文件。
11. 若任一检查不可用、无法强制执行或失败，则丢弃该 scratch 条目；若它是决定性证据，则以 `needs_validation` 保留，并写明确切的提升阻塞项。

[HUNTING.md](HUNTING.md) 与 [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) 以一个完全相同的围栏代码块，把本流程写入猎手与验证者的提示词；其以相同顺序陈述与本列表相同的规则。

对于已复现的检查，记录命令、精确的测试输入、沙箱限制，以及复现所需的、允许列表内的环境变量名与安全的非机密值。绝不捕获或复制环境中的其余变量、被继承的变量、凭据值、认证状态或无关的宿主路径。应从空环境启动，而不是在执行后试图脱敏。

委派之前，Parent 写入 `run-metadata.json`，其中至少包含 `run_id`、`repo`、`target`、`source_ref`、`profile`、`scope_paths`、`budget`（未设置则为 null）、`execution_policy: "sandboxed-source-and-local-only"`、所选配套文件、先前运行路径、共享文件的归属者，以及 `run_status: "in_progress"`。仅在这些事实变化时更新元数据；候选状态属于覆盖台账与 `findings.json`。

## 完整审计规划

本节中的覆盖、先前运行、档位与预算要求仅在完整审计模式下适用。

### 覆盖与先前运行

没有任何一轮检查是完备的。在狩猎开始前构建确定性的覆盖计划，并在每个 Agent 结果返回后更新它。[RECONNAISSANCE.md](RECONNAISSANCE.md) 定义稳定的覆盖单元，[HUNTING.md](HUNTING.md) 定义覆盖评审波次。只有 Parent 能更新台账。

如果存在先前运行，在规划当前运行之前，读取每一个兼容的 `coverage-ledger.json` 与 `findings.json`：

1. 把当前的相关源码与每条先前记录及单元进行比较。仅凭先前的源码引用，不能证明某条路径未发生变化。
2. 仅当先前 `confirmed` 记录的相关源码与条件未变、且其证据仍满足当前契约时，才把它纳入当前候选集。把它关联到一个预置为 `planned` 的当前台账单元，保留其指纹，只把该沿用的根因从猎手任务中排除，并让沿用的记录走当前的最终验证路径；重新核查它的 Phase 3 验证者成为该单元的指派归属者，并将其移入 `candidate`。
3. 当先前 `confirmed` 记录的相关源码发生变化时，创建一个当前的 planned 重新校验单元。不要把该记录放进猎手排除列表。只有当前独立校验确立了当前路径与结果，它才仍是已确认的。
4. 把先前的 `needs_validation`、`deferred`、`blocked`、`out_of_scope` 以及任何源码已变化的单元变成当前工作。仍依赖外部事实的 `needs_validation` 记录，只有在当前源码追踪核查完毕、并通过指纹关联到一个当前 `planned` 单元（该单元验证者的复检提供归属者与证据）之后才可沿用；该记录保留未解决的阻塞项。这些先前状态绝不压制当前单元。
5. 先前同源已覆盖的单元可以为优先级提供参考，但在当前台账中仍然可见。先前 `rejected` 记录只压制未变化的同一失败断言，而不压制对其单元的覆盖；证据一旦变化即产生当前工作。
6. 阅读先前的档位与范围。先前 `quick` 或限定范围的台账只贡献其记录到的证据与缺口，绝不暗示"其余都没问题"。

如果不存在先前台账，在最终覆盖声明中说明这一点。绝不暗示一次运行就能穷尽整个目标。

### 运行档位与范围

在完整审计设置阶段，根据用户请求选定一个档位，或根据目标的规模与风险量级提出一个档位。把它记录在 `run-metadata.json`（`profile`、`scope_paths`）中，并在报告中说明。默认档位为 `standard`。

- **`quick`** — 针对小目标、重复运行或快速初查的一次有界检查。把台账单元粗化为暴露面 × 边界 × 攻击类别的粒度（子系统使用固定的规范标识符 `profile/quick/all-in-scope-subsystems`），恰好运行一个猎手波次加恰好一次最终覆盖评审，并为每个候选使用一个全新验证者，同时承担候选校验与最终记录验证。不得启动后续猎手波次：把评审者接受的发现与重新指派记为 `deferred`。
- **`standard`** — 按本文所述原样执行的工作流。
- **`deep`** — 面向高风险或大型目标。按子系统与生命周期模式拆分台账单元，反复运行评审波次直至干净通过，把候选校验与最终记录验证保持为相互独立的全新 Agent，并给 `prior_covered_same_source` 单元一次独立的第二遍检查。

**限定范围的运行（scoped run）** 只审计一个子集：指名的路径、某个子系统、某个配套领域，或两个源码引用之间的 diff。只为范围内的暴露面预置台账单元，其余一切记为 `out_of_scope` —— 绝不记为 `covered`。限定范围或 `quick` 的运行必须把自身呈现为部分覆盖。

档位改变的是广度与冗余度，绝不是证据门槛。不得因规模调整而取消候选关卡、源码/本地执行边界、`needs_validation` 纪律、schema 校验，或对 `confirmed` 记录的独立验证。

#### 成本预算

台账让消耗可计数：一个单元大约对应一次猎手指派，一个存活的候选对应一到两次验证者指派（取决于档位）。当用户设定了预算——或 Parent 为大型目标提出预算——时，把 `budget` 记录在 `run-metadata.json` 中，作为跨所有阶段的 Agent 调用次数上限。

在启动任何侦察 Agent 之前，先套用严格预算关卡。预留四次基线侦察调用；`quick` 预留一个最终波次后评审者，`standard`/`deep` 预留一个波次后评审者外加一个独立的终局评审者；并至少预留一次验证者调用。只有在对每次额外调用重复套用该关卡之后，才加入聚焦侦察。如果请求的预算无法支撑该最低配置，则不启动任何 Agent：要求更大的预算、更窄的范围或不同的档位。如果请求保持不变，则设置 `run_status: "incomplete"` 与 `incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"`，并报告没有任何审计轮次运行。

按以下顺序消耗预算：

1. 把侦察、每个波次后评审者以及独立的终局评审者都计入 Agent 调用次数。
2. **在狩猎开始前预留评审者与校验成本。** 对 `quick`，预留其唯一一个最终波次后评审者。在每个 `standard` 或 `deep` 猎手波次之前，预留一个紧随其后的波次后评审者，外加一个独立的终局评审者。同时按档位预留验证者成本（每个预期候选约 1 或 2 个 Agent；拿不准时，在评审预留之后预留余额的 30%）。绝不把猎手指派到任何一类预留中。
3. 按优先级顺序把猎手指派到各单元，直到狩猎额度用尽。该波次一结束立即动用预留的波次后评审者；保持终局评审预留与校验预留完好。
4. 在后续波次之前，再次预留其新的波次后评审者。如果剩余预算无法覆盖所需的评审调用与校验预留，则该波次不启动任何猎手，把其 planned 单元标记为 `deferred`，原因为 `budget_cannot_reserve_critics_and_validation`，并使用保留的终局评审者记录由此产生的缺口。

在波次 1 之前，用预置单元、隐含的猎手数量、强制的评审调用、校验预留，以及剩余预算能否覆盖该计划，来更新侦察前估计。如果明显覆盖不了，就明说，并提出收窄范围或改用更粗的档位，而不是悄悄稀释证据。如果后来的事实消耗了必需的终局评审预留，则不启动任何猎手，把所有 planned 工作标记为 deferred，将运行设为 incomplete，原因为 `critic_budget_exhausted`，并且不作任何完整覆盖的声明。

即使设定了严格的总 Agent 预算，意外庞大的候选集，或 Phase 5 中需要另一个独立验证者的实质性替换，仍可能使预算被突破。如果剩余预算无法校验每个候选，则停止狩猎，在预算允许的范围内按指纹顺序校验候选，并设置 `run_status: "incomplete"` 加 `incomplete_reason: "validation_budget_exhausted"`。让每个未校验的指纹都关联到一个带有该未解决原因的 `candidate` 台账单元。不要把未校验的候选放进 `findings.json`，不要把它改标为 `needs_validation`，也不要把该运行报告为已完成。仅当 Phase 6 报告的首节声明候选校验未完成、并列出受影响的指纹与单元时，才允许产出部分报告。绝不悄悄突破用户设定的严格预算。

## 核心原则

### 必须有边界与结果

对每个候选，都要指明低信任主体、被接受的输入或操作、预期控制、被跨越的边界、受影响的主体或资源，以及具体观察到的或所有者可观察到的结果。不得把缺失的最佳实践、猜测的部署行为、通用解析器崩溃或仅影响自身的情况拔高为安全发现项。

### 使用有界的本地证据

静态分析确立源码路径。当所有执行控制齐备时，沙箱化的本地测试可以确定行为：一个最小的函数级 harness、既有单元测试、小型解析器 fixture、虚构租户的集成测试、本地渲染的配置，或有界的隔离 loopback 客户端。在错误的返回值、未授权的虚构记录、sanitizer 报告、策略差异或其他最小影响处即停止。不得把本地检查扩展到最小边界结果之外，也不得产出持久化、故障后或隐匿性材料。

### 尊重源码可见性

部署控制、代理行为、提供方设置、浏览器头、身份策略、broker ACL、打包与拓扑都是真实控制。如果它们是必需的但仓库中没有，既不要假设其存在，也不要假设其不存在。使用 `needs_validation`，写明确切缺失的事实，并给出安全的计划——或由所有者在真实环境观察，或在本地执行。

### 将优先级与确定性分离

只有 `confirmed` 记录才被赋予严重级别。可能性与影响必须反映已演示的条件与结果；总体严重级别不得超过已演示的影响。`needs_validation` 表示某个有源码依据的具体边界假设被阻塞，而不是低置信度的已确认漏洞，它没有严重级别。

用以下锚点校准总体严重级别：

- **critical** — 未认证行为者获得代码执行、对数据存储的完全访问，或可接管任意账户。
- **high** — 行为者完全击溃某个显式安全控制并造成真实后果：身份认证绕过、跨租户读写、影响其他用户的存储型脚本执行、已认证代码执行，或未认证即可远程停止共享服务。
- **medium** — 真实的边界违例，但影响范围有限、前置条件少见，或后果局限于很窄的资源集合。
- **low** — 泄露非机密的内部信息，或需要持续投入却收益甚微的影响。
- **informational** — 已确认但影响极小的观察结果，主要作为更大发现项中的前置条件有用。

high/medium 的判别标准：已演示的结果是对某个有真实后果的操作完全击溃了显式控制，还是仅仅削弱了它？如果说不出具体损害，严重级别就应低于直觉感受。

### 推荐最小有效的源码修复

对每个已确认的发现项，找出代码必须强制执行的不变量，以及在最后一个可信决策点处强制该不变量的最窄源码改动。优先给出相对仓库路径的具体改动与回归测试，而不是泛泛的加固建议。审计只描述修复；不修改目标源码。

## 完整审计工作流

在完整审计模式下，按顺序执行全部六个阶段：

1. **侦察** — 使用 [RECONNAISSANCE.md](RECONNAISSANCE.md) 梳理源码、信任边界、本地构建路径、配套文件选择、先前证据，以及初始的确定性覆盖台账。
2. **以覆盖为导向的狩猎波次** — 使用 [HUNTING.md](HUNTING.md)、[ATTACK-CLASSES.md](ATTACK-CLASSES.md) 与所选领域配套文件，从台账指派相互隔离的猎手，并收集结构化的候选结果。
3. **候选校验** — 合并指纹，并按 [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) 的定义，把每个候选交给一个全新的源码验证者。
4. **结构化输出** — 把所有最终的 `confirmed`、`needs_validation` 与 `rejected` 记录写入 `findings.json`；用 `report-schema.json` 与 `validate-findings.cjs` 校验它，并用 `validate-coverage-ledger.cjs` 校验覆盖声明。
5. **独立记录验证** — 使用全新 Agent 验证最终的源码断言，并核对修正或状态变化。
6. **目标中立报告** — 从最终记录派生 `REPORT.md`、`FINDINGS-DETAIL.md` 与 `NEEDS-VALIDATION.md`，其中不得包含任何针对真实目标探测的指示。

在到达且仅到达以下两种终态之一之前，不得结束运行：(a) Phase 6 的全部产物已写入且两个校验器都通过；或 (b) 已记录 `run_status: "incomplete"` 及其确切原因，且缺口已在报告中披露。绝不在阶段中途停止。

## 反模式

1. 把偏离检查清单的做法当作漏洞上报。
2. 没有可触达边界违例的纵深防御建议。
3. 以有界本地证据不足为由，进行真实环境或共享环境测试。
4. 猜测源码中不存在的提供方、代理、浏览器、身份或部署行为。
5. 把同一主体预期内的权限行使或自影响当作跨边界结果。
6. 报告强于实际观察效果的解析器或运行时影响。
7. 产出无法去重或验证的纯文字猎手结果。
8. 重复上报沿用的同源先前已确认记录，或把它们用作锚定狩猎方向的范例。
9. 给 `needs_validation` 记录指派严重级别。
10. 在独立验证之前撰写报告，或让文字内容与 JSON 不一致。
