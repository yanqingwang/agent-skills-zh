# 对抗式代码审查者

## 描述

这是一个对抗式代码审查 Skill，通过三个具有敌意的审查者角色（破坏者、新员工、安全审计员）强制实现真正的视角切换。每个角色必须至少找出一个问题，不允许用 "LGTM" 蒙混过关。审查结果按严重程度分级；被多个角色同时发现的问题会上调级别。

## 特性

- **三个对抗式角色**：破坏者（生产环境故障）、新员工（可维护性）、安全审计员（参考 OWASP）
- **强制发现问题**：每个角色都必须至少提出一个问题，杜绝走过场式的审查
- **严重程度上调**：被 2 个及以上角色发现的问题上调一级严重程度
- **打破自审陷阱**：用具体方法克服共同心智模型带来的盲点
- **结构化结论**：BLOCK / CONCERNS / CLEAN，附带明确的合并指引

## 用法


```
/adversarial-review              # Review staged/unstaged changes
/adversarial-review --diff HEAD~3  # Review last 3 commits
/adversarial-review --file src/auth.ts  # Review a specific file
```


## 示例

### 示例：合并前审查 PR


```
/adversarial-review --diff main...HEAD
```


生成结构化报告，汇总三个角色的发现，去重并按严重程度排序，最后给出 BLOCK/CONCERNS/CLEAN 结论。

## 解决的问题

当 Claude 审查自己刚写的代码（或刚读过的代码）时，它与作者共享同一套心智模型、假设和盲点。这会导致对"换个新人来审会立刻挑出毛病"的代码给出"看起来没问题"的评价。用户反映这是 AI 辅助开发中最令人头疼的问题之一。

本 Skill 要求你代入对抗式角色，以此强制实现真正的视角切换：每个角色都有不同的关注点、不同的担忧，以及对"坏代码"的不同定义。

## 审查工作流

### 第 1 步：收集变更

根据调用方式确定审查对象：

- **无参数：** 运行 `git diff`（未暂存）+ `git diff --cached`（已暂存）。若两者都为空，则运行 `git diff HEAD~1`（最近一次 commit）。
- **`--diff <ref>`：** 运行 `git diff <ref>`。
- **`--file <path>`：** 读取整个文件。审查重点放在完整文件，而不仅是变更部分。

若未发现任何变更，则停止并报告："Nothing to review."

### 第 2 步：通读完整上下文

对 diff 中的每个文件：

1. 阅读**完整文件**（不仅是改动行）：bug 往往藏在新代码与既有代码的交互里。
2. 明确变更的**目的**：bug 修复、新功能、重构、配置改动、测试。
3. 记录来自 CLAUDE.md、.editorconfig、lint 配置或既有模式的**项目约定**。

### 第 3 步：运行三个角色

依次执行每个角色。每个角色必须至少给出一条发现。如果某个角色没找出任何问题，说明看得还不够仔细，回头再查一遍。

**重要：** 不要弱化发现，不要含糊其辞，不要说"这可能没问题，但是……"：要么有问题，要么没有，直接下结论。

### 第 4 步：去重与汇总

三个角色都报告完毕后：

1. 合并重复的发现（多个角色抓到的同一问题）。
2. 把被 2 个及以上角色发现的问题上调一级严重程度。
3. 生成最终的结构化输出。

## 三个角色

### 角色 1：破坏者

**心态：** "我要想方设法让这段代码在生产环境里崩掉。"

**关注点：**
- 从未校验的输入
- 可能变得不一致的状态
- 无同步的并发访问
- 吞掉异常或返回误导性结果的错误分支
- 关于数据格式、大小或可用性、且可能被违背的假设
- 差一错误、整数溢出、null/undefined 解引用
- 资源泄漏（文件句柄、连接、订阅、监听器）

**审查流程：**
1. 对每个改动过的函数/方法，问："我能塞给它最糟的输入是什么？"
2. 对每个外部调用，问："如果它失败、超时或返回垃圾数据会怎样？"
3. 对每处状态变更，问："如果它执行两次、并发执行、或根本不执行会怎样？"
4. 对每个条件判断，问："如果两个分支都不对会怎样？"

**你必须至少找出一个问题。如果代码确实无懈可击，就记下它所依赖的最脆弱的假设。**

---

### 角色 2：新员工

**心态：** "我刚加入这个团队。半年后我需要在完全没有原作者上下文的情况下理解并修改这段代码。"

**关注点：**
- 不传达意图的命名（`data` 到底指什么？`process()` 又是做什么的？）
- 要读懂就得翻 3 个以上其他文件的逻辑
- 魔数、魔法字符串、没有说明的常量
- 承担不止一件事的函数（名字说做 X，实际还做了 Y 和 Z）
- 缺少类型信息，逼着读者顺着调用链一路追踪
- 与周边代码风格或项目约定不一致
- 测的是实现细节而非行为的测试
- 只描述*做了什么*（冗余）而不解释*为什么*（有用）的注释

**审查流程：**
1. 假装从没见过这套代码库，去读每个改动过的函数。仅凭名字、参数和函数体，你能看懂它在做什么吗？
2. 端到端追踪一条代码路径。你需要打开多少个文件？
3. 检查：新来的贡献者知道该在哪里加一个类似功能吗？
4. 找出"作者知道、读者却不会知道"的地方，也就是固化在代码里的隐性知识。

**你必须至少找出一个问题。如果代码清晰得一目了然，就记下新手最可能感到困惑的地方。**

---

### 角色 3：安全审计员

**心态：** "这段代码会被攻击。我的工作是在攻击者之前找到漏洞。"

**参考 OWASP 的检查清单：**

| 类别 | 检查要点 |
|----------|-----------------|
| **注入** | SQL、NoSQL、操作系统命令、LDAP：任何用户输入未经参数化就进入查询或命令的位置 |
| **认证失效** | 硬编码的凭据、新端点缺少认证校验、会话 token 出现在 URL 或日志里 |
| **数据暴露** | 敏感数据出现在错误消息、日志或 API 响应中；静态存储或传输过程缺少加密 |
| **不安全的默认值** | 调试模式未关闭、宽松的 CORS、通配符权限、默认密码 |
| **缺少访问控制** | IDOR（用户 A 能访问用户 B 的数据吗？）、缺少角色校验、提权路径 |
| **依赖风险** | 带有已知 CVE 的新依赖、锁定在有漏洞的版本、不必要的传递依赖 |
| **机密信息** | 代码、配置或注释里的 API key、token、密码，哪怕标着"临时" |

**审查流程：**
1. 找出代码跨越的每一条信任边界（用户输入、API 调用、数据库、文件系统、环境变量）。
2. 对每条边界：输入是否校验？输出是否净化？是否遵循最小权限原则？
3. 检查：已认证用户能否借这次改动提权？
4. 检查：这次改动是否暴露出新的攻击面？

**你必须至少找出一个问题。如果代码没有任何安全接触面，就记下最接近安全相关假设的那一点。**

## 严重程度分级

| 严重程度 | 定义 | 处理要求 |
|----------|-----------|-----------------|
| **CRITICAL** | 会导致数据丢失、安全漏洞或生产环境中断。合并前必须修复。 | 阻止合并。 |
| **WARNING** | 可能在边界情况下引发 bug、降低性能，或让后续维护者困惑。应在合并前修复。 | 修复，或明确接受风险并给出理由。 |
| **NOTE** | 风格问题、小的改进空间或文档缺失。修了更好。 | 由作者自行决定。 |

**上调规则：** 被 2 个及以上角色标记的问题上调一级（NOTE 变 WARNING，WARNING 变 CRITICAL）。

## 输出格式

按如下结构组织你的审查：


```markdown
## Adversarial Review: [brief description of what was reviewed]

**Scope:** [files reviewed, lines changed, type of change]
**Verdict:** BLOCK / CONCERNS / CLEAN

### Critical Findings
[If any — these block the merge]

### Warnings
[Should-fix items]

### Notes
[Nice-to-fix items]

### Summary
[2-3 sentences: what's the overall risk profile? What's the single most important thing to fix?]
```


**结论定义：**
- **BLOCK**：有 1 条及以上 CRITICAL 发现。解决前不要合并。
- **CONCERNS**：无 CRITICAL，但有 2 条及以上 WARNING。合并风险自负。
- **CLEAN**：只有 NOTE。可以安全合并。

## 反模式

### 本 Skill 不是什么

| 反模式 | 错在哪里 |
|-------------|---------------|
| "LGTM，没发现问题" | 若什么都没找到，说明看得还不够仔细。任何变更都至少存在一处风险、假设或改进空间。 |
| 只报表面问题 | 只提空白/格式，却漏掉 null 解引用，比完全不审还糟。先实质，后风格。 |
| 留情面 | "这也许算个小问题……"：不行，直接点。"当 `user` 为 undefined 时会抛出 NullPointerException。" |
| 复述 diff | "加了这个函数来处理认证"不算发现。它处理认证的方式到底哪里错了？ |
| 忽视测试缺口 | 新代码没有测试就是一条发现，无一例外。测试不是可选项。 |
| 只审改动行 | bug 藏在新代码与既有代码的交互里。要读完整文件。 |

### 自审陷阱

你多半在审查自己刚写或刚读过的代码。你的大脑（权重）形成了产出这段代码的同一套心智模型。因为它符合你的预期，你会自然而然地觉得它没问题。

**打破这一模式的方法：**
1. **自底向上**读代码（从最后一个函数开始，往前倒着看）。
2. 对每个函数，在读函数体**之前**先说出它的契约。函数体对得上吗？
3. 在证明之前，假设每个变量都可能是 null/undefined。
4. 假设每个外部调用都会失败。
5. 问："如果把这次改动整个删掉，会坏掉什么？"如果答案是"什么都不影响"，那这次改动也许是多余的。

## 何时使用

- **合并任何 PR 之前**：尤其是没有人工审查者、由自己提交的 PR
- **长时间编码之后**：疲劳会制造盲点，本 Skill 可以弥补
- **当 Claude 说"看起来没问题"时**：如果轻易就通过了，就跑一遍本 Skill 求个第二意见
- **针对安全敏感代码**：认证、支付、数据访问、API 端点
- **当"感觉哪里不对"时**：相信直觉，做一次对抗式审查
