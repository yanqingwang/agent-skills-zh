# 工作 Skill 分析提示词

## 任务

你将收到 **{name}** 的来源材料（文档、消息、邮件等）。从中提取其工作能力与方法，用于构建工作 Skill。

**原则：只提取与工作相关的内容，忽略闲聊。不要推断；只写有证据的内容，没有证据的地方标注“素材不足”。**

---

## 通用提取维度（适用于所有角色）

### 1. 职责范围

从来源材料中识别：
- 他们负责的系统 / 模块 / 业务线 / 产品
- 他们维护的文档（API 文档、wiki、runbook……）
- 职责边界（哪些是他们的、哪些不是）
- 他们频繁提到的项目代号和业务术语

```
Output format:
Domain: [description]
Core systems: [list]
Maintained docs: [list]
Boundaries: [what they own / what they don't]
```

### 2. 工作流

从任务描述和会议记录中提取：
- 他们接手任务时遵循的步骤
- 写方案 / 文档时的结构习惯
- 如何管理进度、应对截止日期
- 如何处理异常 / 紧急情况

```
Output format:
Taking on tasks: [steps]
Writing proposals: [structure description]
Exception handling: [process]
```

### 3. 输出格式偏好

- 表格 / 列表 / 流程图 / 纯文字
- 结论先行，还是逐步铺垫
- 文档详略程度（极简 / 适中 / 详尽）
- 回复 / 邮件风格

```
Output format:
Document style: [description]
Level of detail: [minimal / moderate / exhaustive]
```

### 4. 经验知识库

他们明确表达过的经验判断、踩坑教训和技术观点（直接引用原话）：

```
- "[original quote or summary]"
- "[original quote or summary]"
```

## 按角色提取

根据 {name} 的角色，聚焦对应维度：

---

### 🖥️ 后端工程师 / 服务端工程师

**技术标准**：
- 技术栈（语言、框架、中间件）
- 命名约定（API 路径风格、变量 / 函数命名）
- API 设计（响应结构、错误码、分页、幂等）
- 数据库偏好（ORM 还是手写 SQL、事务边界）
- 错误处理风格

**代码审查重点**：
- 他们在 CR 里反复提出的问题（N+1、事务、并发安全……）
- 他们的 CR 评论风格（直接 / 委婉，[block]/[suggest] 严重级别……）

**部署与运维**：
- 他们关注的监控指标
- 排查线上问题的步骤
- 变更发布流程

---

### 🌐 前端工程师

**技术标准**：
- 技术栈（框架、状态管理、样式方案）
- 组件拆分原则（何时拆、何时不拆）
- 性能关注点（首屏渲染、懒加载、打包体积……）
- 如何调用 API、处理错误

**工程实践**：
- 代码风格工具（ESLint 规则与 Prettier 配置偏好）
- 测试覆盖期望（对单元 / 集成测试的态度）
- CR 关注点（对无障碍 / 响应式 / 兼容性的在意程度）

---

### 🤖 算法工程师 / 机器学习工程师

**研究与实验**：
- 如何定义问题（怎样拆解一个机器学习问题）
- 实验设计习惯（baseline 选择、消融设计）
- 指标定义偏好（对离线指标与在线指标的态度）
- 常用的模型 / 方法论

**工程落地**：
- 训练框架偏好
- 模型上线流程
- 数据处理规范

**文档与结论**：
- 如何写实验报告（结论导向 / 过程导向）
- 引用的论文或方法论

---

### 📱 产品经理 / 技术产品经理

**需求处理**：
- PRD 结构与详略程度
- 如何定义用户故事 / 需求边界
- 如何与工程对齐（评审风格、变更流程）

**决策框架**：
- 优先级方法（RICE / MoSCoW / 自定义）
- 数据驱动决策与直觉判断的比例
- 如何处理需求冲突

**交付物**：
- 交付的文档类型（PRD / MRD / 原型 / 竞品分析）
- 原型工具偏好
- 参与埋点设计的深度

---

### 🎨 设计师

**设计标准**：
- 使用的设计系统 / 组件库
- 标注风格与交付标准
- 对像素级还原的要求严格程度

**工作流**：
- 从需求到设计方案的步骤
- 如何做设计走查 / 验收评审
- 如何处理工程侧的还原度问题

---

### 📊 数据分析师

**分析方法**：
- 常用分析框架（漏斗 / 同期群 / A/B 测试……）
- SQL 风格（简洁 / 大量注释）
- 数据可视化偏好（图表类型选择）

**报告风格**：
- 结论与数据的比例
- 对“让数据说话”的执行严格程度
- 如何处理数据异常 / 指标定义争议

---

## 输出要求

- 语言：用户的语言
- 无信息的维度：标注为 `(Insufficient source material; consider adding relevant documents)`
- 有来源文本支撑的结论：引用原话
- 输出将直接用于生成 work.md，必须具体可执行；不要用“可能”、“倾向于”这类含糊措辞
