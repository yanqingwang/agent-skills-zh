# Frontend Slides

创建零依赖、动效丰富的 HTML 演示文稿，完全在浏览器中运行。

## 核心原则

1. **零依赖** — 单个 HTML 文件，内联 CSS/JS。无需 npm，无需构建工具。
2. **展示而非告知** — 生成可视化预览，而不是抽象选项。人们通过亲眼所见来发现自己想要什么。
3. **独特设计** — 拒绝千篇一律的"AI 腔"（AI slop）。每一份演示文稿都必须有量身定制之感。
4. **渐进式披露** — 先阅读轻量的风格索引。对于大胆模板（bold templates），使用小预览卡展示风格预览，仅在用户选定该模板后才加载完整的 `design.md`。
5. **固定 16:9 舞台（不可妥协）** — 每份演示文稿都使用 1920×1080 的幻灯片画布，整体等比缩放以适配视口。幻灯片在包括手机在内的所有屏幕上都必须保持 16:9。不要为适配设备而重排幻灯片内容。

## 设计美学

你倾向于收敛到平庸、"大众化"的输出。在前端设计中，这会造成用户所说的"AI 腔"（AI slop）美学。要避免这一点：做出有创意、有辨识度、令人惊喜愉悦的前端。

关注以下几点：

- 字体排印：选择优美、独特、有趣的字体。避免 Arial、Inter 等平庸字体；改用能提升前端美学的独特字体。
- 色彩与主题：坚持一种统一的美学。使用 CSS 变量保持一致性。主色搭配鲜明的点缀色，胜过畏手畏脚、平均分配的配色。可以从 IDE 主题和各类文化美学中汲取灵感。
- 动效：用动画制造效果和微交互。HTML 场景优先使用纯 CSS 方案；React 场景在可用时使用 Motion 库。聚焦高冲击力的瞬间：一次精心编排的页面加载、配合错落有致的渐次显现（animation-delay），比零散的微交互更能带来愉悦感。
- 背景：营造氛围与纵深感，而不是默认使用纯色。叠加 CSS 渐变、使用几何图案，或添加契合整体美学的情境化效果。

避免俗套的 AI 生成美学：

- 被过度使用的字体家族（Inter、Roboto、Arial、系统字体）
- 陈词滥调的配色方案（尤其是白底紫色渐变）
- 一眼可预测的布局与组件模式
- 缺乏情境个性、千篇一律的模板化设计

发挥创意解读需求，做出真正契合情境、出人意料的选择。在明暗主题、不同字体、不同美学之间变化。你在多次生成中仍容易收敛到常见选择（例如 Space Grotesk）。要避免这一点：跳出思维定式至关重要！

## 固定舞台规则

以下不变量适用于每一份演示文稿中的每一张幻灯片：

- 每份演示文稿都有一个填满浏览器窗口的视口容器（viewport wrapper）。
- 每张幻灯片都在固定的 1920×1080 舞台内制作。
- 舞台等比缩放以适配视口。允许出现上下/左右黑边（letterbox/pillarbox）；绝不允许重新布局内容。
- 不要使用响应式断点为手机重排幻灯片内容。
- 在 1920×1080 设计尺寸下使用固定的幻灯片内部尺寸。
- 幻灯片的可见性必须由 `.active` / `.visible` 控制，使用来自 `viewport-base.css` 的 `visibility`、`opacity` 和 `pointer-events`。不要用 `display: none` / `display: block` 来切换幻灯片；后续的布局类（如 `.slide-content { display: flex; }`）可能覆盖它们，导致所有幻灯片同时可见。
- `clamp()` 仅用于舞台之外的非幻灯片 UI，或在整舞台不切实际时用于小型降级预览。
- 包含 `prefers-reduced-motion` 支持
- 不要直接对 CSS 函数取负（`-clamp()`、`-min()`、`-max()` 会被静默忽略）— 应改用 `calc(-1 * clamp(...))`

**生成时，阅读 `viewport-base.css` 并将其完整内容包含在每份演示文稿中。**

### 内容密度模式

询问用户这份演示文稿主要是阅读型还是演讲型，然后围绕该答案进行设计：

| 密度模式 | 最适合 | 设计行为 |
| ------------- | -------- | --------------- |
| **低密度 / 演讲主导** | 公开演讲、主旨式分享、现场讲解 | 每张幻灯片一个观点、大字号、强视觉层级、充足的留白、最多 1-3 条要点，必要时增加幻灯片数量 |
| **高密度 / 阅读优先** | 报告、讲义、异步审阅、详细的内部文档 | 幻灯片更加自包含、结构化的网格/表格/注释、在可读的前提下每张 4-8 条要点或 4-6 张卡片、间距更紧凑但仍经过刻意设计 |

基线限制仍然适用：不滚动、不溢出、面板不重叠、文字不小于舒适阅读尺寸。如果内容超出所选的密度模式，应拆分为更多幻灯片，而不是一味缩小直到拥挤不堪。

## Phase 0：判断模式

判断用户想要什么：

- **Mode A：新建演示文稿** — 从零开始创建。进入 Phase 1。
- **Mode B：PPT 转换** — 转换 .pptx 文件。进入 Phase 4。
- **Mode C：增强** — 改进现有的 HTML 演示文稿。阅读它、理解它、增强它。**遵循下文的 Mode C 修改规则。**

### Mode C：修改规则

增强现有演示文稿时，最大的风险是固定舞台适配问题：

1. **添加内容之前：** 统计现有元素数量，对照密度上限进行检查
2. **添加图片：** 将图片放入 1920×1080 幻灯片画布内。如果幻灯片内容已达上限，拆分为两张幻灯片
3. **添加文字：** 每张幻灯片最多 4-6 条要点。超出上限？拆分为续接幻灯片
4. **任何修改之后都要验证：** 幻灯片舞台仍保持 16:9、文字不溢出所在卡片、面板不重叠，且 1280×720 截图加上一个手机视口的截图显示正常
5. **主动重组：** 如果修改会导致溢出，自动拆分内容并告知用户。不要等着被要求

**向现有幻灯片添加图片时：** 先把图片移到新幻灯片，或先削减其他内容。绝不在没有检查现有内容是否已填满 1920×1080 幻灯片舞台的情况下添加图片。

## Phase 1：内容收集（新建演示文稿）

**一次性问完所有问题**，让用户一口气填写完毕。如果当前环境提供原生的结构化提问 UI，就使用它；否则用一条简洁消息提出，选项编号清晰：

**问题 1 — 用途** (header: "Purpose")：
这份演示文稿是做什么用的？选项：Pitch deck（路演提案）/ Teaching-Tutorial（教学教程）/ Conference talk（大会演讲）/ Internal presentation（内部演示）

**问题 2 — 篇幅** (header: "Length")：
大约需要多少张幻灯片？选项：Short 5-10（短）/ Medium 10-20（中）/ Long 20+（长）

**问题 3 — 内容** (header: "Content")：
你是否已备好内容？选项：All content ready（内容齐备）/ Rough notes（粗略笔记）/ Topic only（仅有主题）

**问题 4 — 密度** (header: "Density")：
你希望整体信息密度如何？选项：

- "Low density / speaker-led"（低密度 / 演讲主导）— 大想法、少文字、更多视觉呼吸空间
- "High density / reading-first"（高密度 / 阅读优先）— 更自包含的细节，便于异步阅读

**Phase 1 期间不要询问行内编辑。** 用户不应在看到草稿之前就选择编辑行为。行内编辑是草稿完成之后才提供的默认能力：默认包含它，除非用户明确要求锁定/仅导出的文件。

记住用户选择的密度。它影响幻灯片数量、字号比例、每张幻灯片的文字量、布局密度，以及是偏重电影感演讲幻灯片还是自包含阅读幻灯片。

如果用户有现成内容，请他们提供。

### Step 1.2：图片评估（如提供了图片）

如果用户选择 "No images"（无图片）→ 跳到 Phase 2。

如果用户提供了图片文件夹：

1. **扫描** — 列出所有图片文件（.png、.jpg、.svg、.webp 等）
2. **逐一查看图片** — 使用 Agent 可用的图像理解能力。如果无法读取图片，则依据文件名/元数据，仅在必要时请用户澄清
3. **评估** — 对每张图片：它展示了什么、USABLE（可用）还是 NOT USABLE（不可用）、附上原因、代表的概念、主色调
4. **共同设计大纲** — 精选的图片与文字共同决定幻灯片结构。这不是"先规划幻灯片再塞入图片"——而是从一开始就围绕两者设计（例如：3 张截图 → 3 张功能幻灯片，1 个 logo → 标题/结尾幻灯片）
5. **确认大纲** — 在可用时使用同样的结构化提问机制："这份幻灯片大纲和图片选择是否合适？"选项：Looks good（没问题）/ Adjust images（调整图片）/ Adjust outline（调整大纲）

**预览中的 logo：** 如果识别出了可用的 logo，在 Phase 2 中将其（base64）嵌入每个风格预览——让用户看到自己的品牌以三种不同方式呈现。

## Phase 2：风格探索

**这是"展示而非告知"的阶段。** 大多数人无法用语言表达自己的设计偏好。

### Step 2.0：直接生成 3 个风格预览

根据用途、受众、情绪和内容密度，生成 3 个风格迥异的单页 HTML 预览，展示字体排印、色彩、动画和整体美学。

不要询问用户是否想要选项或预设选择器。默认的探索体验始终是视觉对比。

如果用户已经给出了氛围偏好（vibe），就采用它。如果没有，则从场合、受众、内容和利害关系推断可能的情绪。保持选项足够多样，让用户可以通过视觉直接反应，而不必事先用语言表达品味。

如果用户明确点名了某个预设或大胆模板，将其作为其中一个选项，并围绕它生成其余的预览位。

阅读 [STYLE_PRESETS.md](STYLE_PRESETS.md) 了解稳妥预设候选。如果 [bold-template-pack/selection-index.json](bold-template-pack/selection-index.json) 存在，也阅读这个精简索引，但先不要读任何 `design.md` 文件。

| 情绪 | 建议预设 |
| ------------------- | -------------------------------------------------- |
| 震撼/自信 | Bold Signal, Electric Studio, Dark Botanical |
| 兴奋/激昂 | Creative Voltage, Neon Cyber, Split Pastel |
| 平静/专注 | Notebook Tabs, Paper & Ink, Swiss Modern |
| 灵感迸发/动情 | Dark Botanical, Vintage Editorial, Pastel Geometry |

**预览组合规则：**

- 默认生成 3 个预览：1 个来自 `STYLE_PRESETS.md` 的稳妥预设（safe preset）、至少 1 个来自 `bold-template-pack/selection-index.json` 的大胆模板（bold template），以及 1 个 wildcard（自由发挥）。
- wildcard 位可以是第二个大胆模板，也可以是自生成的定制设计。选择能为用户的场合、受众、情绪和内容制造最强烈、最有用对比的那一个。
- 不要强求每个富表现力的选项都来自模板库。如果需求简报中存在比可用模板更敏锐、更具体的设计机会，就用 wildcard 位放手设计。
- 对于保守或高风险场合的演示文稿，让稳妥预设格外克制；选择一个沉稳、正式度更高的大胆模板；让 wildcard 位要么是另一个克制模板，要么是显得权威而非花哨的定制设计。
- 对于表现型演示文稿，让稳妥预设作为可读的保底；选择一个强力的大胆模板；让 wildcard 位大胆冒险、贴合情境，并且明显区别于另外两个预览。
- 如果大胆模板的匹配度不佳，就把 wildcard 位用作定制设计，或退回到另一个稳妥预设，不要强行套用模板。

**定制 wildcard 设计规则：**

- 遵循上文"设计美学"一节：不要平庸的"AI 腔"，不要默认的字体/配色/布局，不要白底紫渐变的俗套，不要千篇一律的仪表盘/卡片外观。
- 契合用户陈述的场合、受众、情绪/氛围和内容密度。定制设计应当让人感到是为这份演示文稿专门创作的，而不仅仅是"好看"。
- 确立一个深思熟虑的视觉主张：独特的字体排印、贯彻始终的配色、可辨识的布局系统，以及一个强力的氛围或图形手法。
- 保证它能扩展为整套演示文稿。预览必须暗示一个可延展的设计系统，能够扩展到章节页、内容页、引用页、对比页和结尾页。
- 遵守固定 1920×1080 舞台规则，并通过与其他选项相同的预览真实性检查。
- 绝不在幻灯片本身渲染 "custom"、"wildcard"、"AI-generated" 等字样或设计过程标签。

**大胆模板选择规则：**

- 将用户用途和情绪与 `mood`、`tone`、`best_for`、`avoid_for`、`formality`、`density`、`scheme` 字段进行匹配。
- 把 `best_for` 示例当作软性信号，而不是严格的行业过滤条件。
- 保持三个预览彼此真正不同。
- 选定大胆模板候选后，只按选择索引中 `preview_md` 路径阅读这些候选的 `preview.md` 文件。
- `preview.md` 仅用于标题页预览。在用户选定最终模板之前，不要读取完整的 `design.md` 文件。
- 除非选定模板的最终 `design.md` 缺少关键实现细节，否则不要阅读或复制 `template.html`。

**预览真实性规则（不可妥协）：**

- 每个风格预览都必须看起来像用户演示文稿里真实的第一页，而不是诊断卡片。
- 绝不在幻灯片上渲染内部流程文字：不得出现 `preview`、`generated from`、`preview.md`、`template`、`preset`、`style option`、`Option A/B/C`、文件名、路径或来源文档标签。
- 绝不在幻灯片本身渲染模板名或 slug 名。模板/风格名称只能出现在发给用户的消息中。
- 绝不把用户的需求备注当作幻灯片内容，例如 "sharp and provocative"、"safe option"、"bold option"、"for internal sharing"、"audience: ..."，除非用户明确希望这句话原样出现在演示文稿中。
- 如果幻灯片需要界面装饰元素（chrome），只使用真实的演示文稿元素：文稿标题、章节标题、日期、作者、公司、页码，或用户材料中真实的内容短语。
- 打开预览之前，检查可见文字，发现任何内部元数据就立即修改。

将预览保存到 `.frontend-slides/slide-previews/`（style-a.html、style-b.html、style-c.html）。每个预览都应自包含且精简，展示一张带动画的标题页。

为用户自动打开每个预览。

### Step 2.1：用户选择

询问 (header: "Style")：
你更喜欢哪个风格预览？选项：Style A: [Name] / Style B: [Name] / Style C: [Name] / Mix elements（混搭元素）

如果选择 "Mix elements"（混搭元素），询问具体细节。

## Phase 3：生成演示文稿

使用 Phase 1 的内容（纯文字，或文字 + 精选图片）和 Phase 2 的风格，生成完整的演示文稿。

如果提供了图片，幻灯片大纲已在 Step 1.2 中纳入它们。如果没有，CSS 生成的视觉元素（渐变、形状、图案）将提供视觉趣味——这是一条完整支持的一等公民路径。

在整套演示文稿中贯彻用户选择的密度：

- **低密度 / 演讲主导：** 使用更多幻灯片、每张承载更少观点。偏重大标题、短语、视觉隐喻、章节节拍、引用/宣言页，以及适合演讲者掌控的节奏。
- **高密度 / 阅读优先：** 让幻灯片更自包含。使用结构化网格、对比表格、带注释的图示、图注和简明的说明文字。保持强烈的层级感，使其看起来是精心设计的，而不是把文档直接贴到幻灯片上。

如果用户表述的需求两者兼具，选择更接近的模式而不是发明一个中间选项：面向现场观众的说服型默认低密度；异步传阅或详细审阅默认高密度。

绝不让高密度沦为视觉杂乱。如果高密度幻灯片开始溢出，就拆分它，或重新设计为更清晰的结构。

如果用户从 `bold-template-pack` 中选择了一个大胆模板，在生成前阅读该模板完整的 `design.md`。不要阅读其他大胆模板。把 `design.md` 当作设计配方：

- 保留其字体、配色、装饰语汇、间距节奏和组件语法。
- 将最终演示文稿生成为固定 1920×1080 舞台、等比缩放适配视口，无论源模板原本使用的是 `deck-stage.js` 还是视口流式 CSS。
- 把 `design.md` 中的视口流式数值当作设计比例，换算为 1920×1080 舞台坐标。不要在最终演示文稿中把它们保留为实时的视口重排规则。
- 保持输出为单个自包含的 Frontend Slides HTML 文件。
- 不要照抄演示页内容，也不要过于刻板地模仿源模板。
- 仅在万不得已时把 `template.html` 用作所选模板的实现参考。
- 生成之后，在浏览器渲染截图中同时验证内容溢出和面板重叠。仅靠 `scrollHeight` 检查并不够，因为网格面板可能在视觉上互相遮挡。

如果用户选择了自生成的定制 wildcard，就把该预览的 CSS 和布局当作设计配方：

- 保留其字体、配色、装饰语汇、间距节奏、网格逻辑和组件语法。
- 在整套演示文稿中延展同一套视觉系统。用户已选定定制方向后，不要切换到预设或大胆模板。
- 缺失的幻灯片布局要从该系统中设计出来，而不是从其他风格移植模式。
- 保持输出为固定舞台、单文件，并像其他所有演示文稿一样经过视觉验证。

**生成之前，阅读以下支持文件：**

- [html-template.md](html-template.md) — HTML 架构与 JS 特性
- [viewport-base.css](viewport-base.css) — 强制使用的 CSS（完整包含）
- [animation-patterns.md](animation-patterns.md) — 与所选气质相符的动画参考

**关键要求：**

- 单个自包含 HTML 文件，所有 CSS/JS 内联
- 在 `<style>` 块中包含 viewport-base.css 的全部内容
- 使用来自 Fontshare 或 Google Fonts 的字体——绝不用系统字体
- 添加详细注释，解释每个部分
- 每个部分都需要清晰的 `/* === SECTION NAME === */` 注释块

## Phase 6：分享与导出（可选）

交付之后，**询问用户：**_"是否想分享这份演示文稿？我可以将其部署到一个在线 URL（包括手机在内的任何设备都能访问），或将其导出为 PDF。"_

选项：

- **部署到 URL** — 可分享的链接，任何设备都能访问
- **导出为 PDF** — 通用文件，可用于邮件、Slack、打印
- **两者都要**
- **不用了**

如果用户拒绝，就此停止。如果选择其中之一或两者都要，继续下文。

### 6A：部署到在线 URL（Vercel）

这会将演示文稿部署到 Vercel——一个免费的托管平台。链接在任何设备（手机、平板、笔记本）上都可用，并保持在线，直到用户将其下线。

**如果用户从未部署过，请逐步引导：**

1. **检查是否安装了 Vercel CLI** — 运行 `npx vercel --version`。如果未找到，先安装 Node.js（macOS 上 `brew install node`，或从 https://nodejs.org 下载）。

2. **检查用户是否已登录** — 运行 `npx vercel whoami`。
   - 如果尚未登录，解释：_"Vercel 是一项免费托管服务。部署需要账号。我来带你一步步完成："_
     - 第 1 步：请用户在浏览器中打开 https://vercel.com/signup
     - 第 2 步：可以用 GitHub、Google 或邮箱注册——哪种最方便就用哪种
     - 第 3 步：注册完成后，运行 `vercel login` 并按提示操作（会打开浏览器窗口进行授权）
     - 第 4 步：用 `vercel whoami` 确认登录成功
   - 等待用户确认已登录后再继续。

3. **部署** — 运行部署脚本：

   ```bash
   bash scripts/deploy.sh <path-to-presentation>
   ```

   该脚本接受文件夹（含 index.html）或单个 HTML 文件。

4. **分享 URL** — 告诉用户：
   - 在线 URL（来自脚本输出）
   - 任何设备都能访问——可以通过短信、Slack、邮件分享
   - 之后要下线：访问 https://vercel.com/dashboard 删除该项目
   - Vercel 免费额度很宽裕——不会产生费用

**⚠ 部署注意事项：**

- **本地图片/视频必须随 HTML 一起部署。** 部署脚本会自动检测 HTML 中通过 `src="..."` 引用的文件并一并打包。但如果演示文稿通过 CSS `background-image` 或非常规路径引用文件，可能会被遗漏。**部署之前务必验证：** 打开部署后的 URL，检查所有图片是否加载。如果有损坏，最稳妥的修复方法是把 HTML 和所有资源放进同一个文件夹，部署该文件夹而不是单独的 HTML 文件。
- **资源较多时优先部署文件夹。** 如果演示文稿位于一个文件夹中且图片与之同在（例如 `my-deck/index.html` + `my-deck/logo.png`），直接部署文件夹：`bash scripts/deploy.sh ./my-deck/`。这比部署单个 HTML 文件更可靠，因为整个文件夹内容会原样上传。
- **带空格的文件名可用，但可能引发问题。** 脚本能处理文件名中的空格，但 Vercel URL 会把空格编码为 `%20`。尽量避免图片文件名中含空格。如果用户的图片文件名带空格，脚本可以处理——但如果图片仍然损坏，把文件名中的空格改为连字符即可修复。
- **重新部署更新的是同一个 URL。** 对同一份演示文稿再次运行部署脚本会覆盖上一次部署。URL 保持不变——无需分享新链接。

### 6B：导出为 PDF

这会将每张幻灯片截图并合成为一个 PDF。非常适合作为邮件附件、嵌入文档或打印。

**注意：** 动画和交互不会保留——PDF 是静态快照。这是正常且符合预期的；要向用户提及，以免他们感到意外。

1. **运行导出脚本：**

   ```bash
   bash scripts/export-pdf.sh <path-to-html> [output.pdf]
   ```

   如果未指定输出路径，PDF 会保存在 HTML 文件旁边。

2. **幕后过程**（向用户简要解释）：
   - 无头浏览器以 1920×1080（标准宽屏）打开演示文稿
   - 逐张对幻灯片截图
   - 所有截图合成为一个 PDF
   - 脚本需要 Playwright（一个浏览器自动化工具）——如果缺失会自动安装

3. **如果 Playwright 安装失败：**
   - 最常见的问题是 Chromium 下载失败。运行：`npx playwright install chromium`
   - 如果仍然失败，可能是网络/防火墙问题。请用户换一个网络再试。

4. **交付 PDF** — 脚本会自动打开它。告诉用户：
   - 文件位置和大小
   - 到处都可用——邮件、Slack、Notion、Google Docs、打印
   - 动画被替换为最终视觉状态（看起来依然精美，只是静态）

**⚠ PDF 导出注意事项：**

- **首次运行较慢。** 脚本会安装 Playwright 并将 Chromium 浏览器（约 150MB）下载到临时目录。这一步每次运行只发生一次。提醒用户首次可能需要 30-60 秒——同一会话内的后续导出会更快。
- **幻灯片必须使用 `class="slide"`。** 导出脚本通过查询 `.slide` 元素来查找幻灯片。如果演示文稿使用了其他类名，脚本会报告 "0 slides found" 并失败。本 Skill 生成的所有演示文稿都使用 `.slide`，因此这只对外部创建的 HTML 有影响。
- **本地图片必须能通过 HTTP 加载。** 脚本会启动一个本地服务器并通过它加载 HTML（这样 Google Fonts 和相对图片路径才能生效）。如果图片使用绝对文件系统路径（如 `src="/Users/name/photo.png"`）而不是相对路径（如 `src="photo.png"`），将无法加载。生成的演示文稿始终使用相对路径，但转换或用户提供的演示文稿未必如此——需要检查并在必要时修复。
- **本地图片会出现在 PDF 中**，只要它们与 HTML 文件位于同一目录（或其相对路径下）。导出脚本会通过 HTTP 提供 HTML 所在的父目录，因此 `src="photo.png"` 这类相对路径能正确解析——包括带空格的文件名。如果图片仍未出现，检查：(1) 图片文件确实存在于所引用路径，(2) 路径是相对路径，而不是 `/Users/name/photo.png` 这样的绝对文件系统路径。
- **大型演示文稿会生成较大的 PDF。** 每张幻灯片都被截取为完整的 1920×1080 PNG 截图。18 页的演示文稿可能生成约 20MB 的 PDF。如果 PDF 超过 10MB，询问用户：_"PDF 大小为 [size]。需要我压缩它吗？清晰度会略微下降，但文件会小得多。"_ 如果需要，用 `--compact` 标志重新导出：
  ```bash
  bash scripts/export-pdf.sh <path-to-html> [output.pdf] --compact
  ```
  这会以 1280×720 而不是 1920×1080 渲染，通常可将文件大小削减 50-70%，视觉差异极小。
