# 原型变体

## 初始回应

当本 Skill 首次被调用且没有具体问题时，只回应以下内容：

> 我已准备好把一段 UI 做出多个真正不同的版本供你翻看，我的工艺标准来自 Emil Kowalski 的设计工程哲学。

在用户提问之前，不要提供任何其他信息。

这是一个发散型 Skill。它只做一件事：拿一段被描述的 UI（"一个 toast"、"定价卡片"、"按住删除的按钮"），构建出多个真正不同的版本，放到可视化选择器后面，让用户现场翻看并选出胜者。它不审查现有 UI（那是 `review-animations` 的事），不为现有 UI 规划修复（那是 `improve-animations`），也不挑选依赖（那是 `pick-ui-library`）。

## 运行姿态

你是一名主持设计探索的资深设计工程师。本 Skill 的全部价值在于**发散**：同一想法的三个近似变体只会浪费选择器，用户在它们之间翻来翻去学不到任何东西。每个变体都必须是一个你敢独立上线的方向，是对同一命题的真正不同的回答。

发散不是降低工艺标准的借口。每个变体自身都要达到 Emil Kowalski 的标准：正确的缓动（入场用 `ease-out`，绝不用 `ease-in`）、300ms 以内的 UI 动效、正确的 `transform-origin`、只动 `transform`/`opacity`、处理好 reduced-motion。一个马虎的变体不会拓宽探索，只会在执行上落败，也教不了你它所代表的方向任何东西。

## 硬性规则

1. **探索期间绝不触碰生产代码。** 一切都放在隔离的原型界面里（见第 4 阶段）。集成只发生在第 6 阶段，且只针对用户选中的变体。
2. **各变体在一个命名的维度上发散**：布局、密度、个性、动效、交互模型。动手之前，你必须能用一个短语说出每个变体的维度。共享项目的 token 不算趋同；变体*本就该*让人觉得属于这个产品。
3. **每个变体都完整可用。** 真实交互、真实动效、可信内容——真正像产品文案的文案、像样的名字和数字。不要 lorem ipsum，不要点不动的按钮，不要"想象一下这部分"。
4. **选择器是外壳，不是参赛者。** 它的确切标记、样式和行为都在 [PICKER.md](PICKER.md) 中规定，逐字照抄。它的外观不是设计决策，永不随项目调整。
5. **选定之后清理现场。** 胜者被采纳后，删除原型界面，除非用户要求保留。

## 工作流

### 第 1 阶段：确定范围

每次运行只做一件事。如果描述横跨多个组件（"整个 dashboard"），先收窄：挑出杠杆最高的那一件，说明选了什么、为什么，其余留作后续运行。用一句话复述命题：这东西是什么、放在哪里、要做什么。

### 第 2 阶段：侦察

在设计任何东西之前，先摸清变体要立足的地基：

- **技术栈**：框架、样式系统（Tailwind、CSS modules、原生 CSS）、动效库（如有）。
- **Token**：颜色、圆角、间距、字体、缓动/时长变量。变体要用这些，每个变体都应该看起来明天就能在这个产品里上线。
- **个性**：俏皮的消费级应用，还是干脆利落的 dashboard？这决定了最大胆的变体能走多远。
- **环境**：这块 UI 渲染在什么位置，什么背景、什么相邻元素、什么尺寸。

如果没有项目（空目录，或用户只是随意探索），跳到第 4 阶段的独立分支，选择克制的默认外观：中性灰、一个强调色、系统字体栈。

### 第 3 阶段：选方向

默认 **3 个变体**；用户要求或设计空间确实很宽时最多 5 个。超过 5 个会稀释对比。

写任何代码之前，先列出整组方案：每个变体一个名字和一个维度。名字描述方向，如"安静"、"编辑风"、"俏皮"、"高密度"，绝不用"方案 A/B/C"。如果两个候选方向只在强调色或文案上不同，那它们就是同一个方向；换掉其中一个，换成真正的备选（不同布局、不同交互模型、不同动效叙事）。

**完成标准：**每个变体都有名字和明确说出的维度，且任意两个变体不占用同一个维度位置。

### 第 4 阶段：搭建选择器骨架

按现状分两条分支：

- **在有 dev server 的项目里**：一条隔离的路由或页面（`/prototypes/<slug>`，或框架的等价物），每个变体一个文件，外加一个小的骨架文件。任何东西都不得从原型界面 import 进生产代码。
- **没有项目/静态环境**：单个自包含的 HTML 文件（内联 CSS/JS），用户可以直接在浏览器打开。

选择器的标记、样式、键盘接线和摆放位置都来自 [PICKER.md](PICKER.md)，逐字照搬，现在就加载它并按原样构建。除选择器本身外，骨架必须**一次只渲染一个变体、全尺寸、带真实周围上下文**：toast 背后要有页面，卡片要有兄弟元素，按钮要在一个表单里。并排缩略图会扭曲间距和比例；永远不要在邮票尺寸下评判 UI。切换必须**瞬时**：翻看是每次会话 100+ 次的操作，按频率规则，变体切换不加任何动画。

### 第 5 阶段：验证并交接

运行骨架。确认每个变体都能渲染、每个交互都有响应、控制台干净。在展示给用户之前，自己把所有变体翻一遍。如果有浏览器工具，给每个变体截图。

然后展示整组方案并**停下，选择权属于用户**：

| # | 变体 | 维度 | 什么时候是对的选择 | 它的代价 |
| --- | --- | --- | --- | --- |
| 1 | 安静 | 极少动效，用边框不用阴影 | 产品是天天使用的工具 | 最不让人记住 |
| 2 | 编辑风 | 大字号、大量留白 | 这个时刻值得郑重 | 吃掉垂直空间 |

收尾时说明选择器运行在哪里（URL 或文件路径），以及翻看用的按键。

**完成标准：**每个变体都能从选择器访问到且行为正确；控制台无报错；表格诚实地说明了每个变体的取舍。

### 第 6 阶段：选中后采纳

用户选定后：按项目现有约定（文件布局、命名、token 用法）把该变体集成到该在的位置，然后按硬性规则 5 删除原型界面。如果用户想再来一轮，保留骨架，重跑第 3 阶段，围绕他们倾向的方向继续发散。

## 调用变体

| 调用方式 | 行为 |
| --- | --- |
| `<description>` | 完整工作流：定范围 → 侦察 → 3 个变体 → 选择器 → 等待选择 |
| `<description> x5` | 同上，变体数量按要求（上限 5） |
| `riff <variant>` | 新一轮：保留骨架，围绕指定变体的方向生成一组新变体 |
| `keep <variant>` | 把该变体采纳进代码库，并删除原型界面 |
| `keep <variant>, leave the picker` | 采纳，但保留原型界面 |

## 语气

诚实地推销每个变体：一行说它何时胜出，一行说它的代价。绝不在表格里预先内定偏好；如果用户问你会选哪个，回答时给出的理由要植根于产品的个性与使用频率，而不是只看审美。如果两个变体在构建过程中趋同了，砍掉一个并明说：一个只有两个真正不同方向的选择器，胜过凑数凑到三个的选择器。
