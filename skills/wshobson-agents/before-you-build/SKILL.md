# 动手之前（Before You Build）

在实现之前运行一次精简的事前验尸（pre-mortem）。目标不是阻止构建，而是识别风险最高的假设、最小的验证步骤，以及在证据改善之前应当暂缓的构建范围。

## 何时使用

当用户要求构建或发布上线以下内容时，使用本 Skill：

- 新产品、MVP、原型、落地页、SaaS 应用、市场平台、内容站点、Agent 工作流或内部工具
- 一项重大功能，其在采用、营收、留存、信任或分发上的影响尚不明确
- 面向公开发布的资产，而糟糕的定位可能浪费开发或推广投入

当任务是范围狭窄的实现修复、重构、测试修复、依赖更新，或已有明确验收标准且经过验证的变更时，跳过本 Skill。

## 风险清单

从以下风险维度审视这个想法：

- **需求（Demand）：** 是否有证据表明某个具体的买家或用户迫切需要它？
- **定位（Positioning）：** 目标用户能否用一句话理解它是什么、为什么重要？
- **变现（Monetization）：** 是否存在一条可信的付费、预算或战略价值路径？
- **留存（Retention）：** 用户在首次尝试之后，是否有理由再次回来？
- **信任（Trust）：** 产品是否要求用户给予公信力、数据访问权限、集成或行为改变，而用户可能会抗拒？
- **分发（Distribution）：** 是否存在一条可重复触达目标用户的路径？
- **功能采用（Feature adoption）：** 对于功能类工作，这个功能会改变用户行为，还是只是增加表面积？

如果结论不明显，使用 `references/risk-checklist.md` 获取更深入的问题。

## 输出格式

保持回复简短、面向决策：

1. **风险判定（Risk verdict）：** 低、中或高风险，并用一句话说明原因。
2. **核心假设（Main assumption）：** 最有可能让项目失败的那一个假设。
3. **优先寻找的证据（Evidence to find first）：** 在构建更多内容之前，最小的有效信号。
4. **下一步行动（Do next）：** 一个具体的验证步骤，或缩小后的构建范围。
5. **暂缓项（Delay）：** 现阶段不要构建什么。

## 指导原则

- 对薄弱证据直言不讳，但不要全盘否定用户的想法。
- 优先选择更小的验证步骤，而不是庞大的调研计划。
- 把产品风险与工程难度区分开。
- 如果想法已经过验证，说明哪些证据使其风险降低，并建议最小的实现切片。
- 如果事实缺失，指出缺失的证据，而不是编造市场论断。
